# mcloud-plugin

把 [mcloud](https://github.com/asunajs/mcloud)（中国移动云盘的 Rust 自动化服务）**用 JS/TS 重写一份**，
作为 [rust-plugin-panel](https://github.com/asunajs/panel) 的插件跑起来。

两个目标**同等重要**：

1. **功能**：mcloud 的任务与界面在插件形态下真的能用
2. **压力与优化**：它是这个面板能碰到的最大的东西 —— 用它把面板的边界压出来，
   每压出一个就回面板仓库修掉，并在 [`docs/findings.md`](docs/findings.md) 记下
   「怎么测的、什么数、改了什么」

> **状态（2026-10-14）**：签到族 8 条 + 通知 / 任务拓展 / 上传链 / 消息推送 /
> app-task（矩阵只读 + 动作写）/ **直播一族（口令只读 + 领小红花写 + 共享口令池 +
> 直播日程「门」+ **听弹幕口令**）** 都已落地，对着 mock 在**真面板**里端到端跑通
> （`scripts/e2e-mock.sh`，含一个手写的 SockJS 端点），真 ARM64 CI 全绿。
> 30 条任务里 26 条 `implemented: true`（剩下 4 条各自那行注释写了为什么）。
>
> **直播这一族在真机上验到哪儿了**（细节见 F-030 ~ F-034）：**全链已通** ——
> 门 → `userToken`（WS 凭据）→ `roomBeat`（聊天室号）→ `member/apply`（进房间）→
> WS + PROVISION → **真弹幕文本** → 口令进池 → 按 mcloud 的六步链**领到小红花**。
> **直播自动定时（`live-auto`，mcloud 的 `live_auto`）**：时刻 = 「下一场」+ 1 小时，
> 每 5 分钟重算一次、**一个上游请求都不发**；听弹幕那条链被判"门关着"时就睡到那一刻。
> ⇒ **没开播时面板不再空问门**（见 F-037）。

> 验收读数（2026-10-14，房间 147868）：**三个账号各自听完并各领到 10 朵** ——

## 先跑起来（不用真账号）

```bash
# ① 一整套本地验证：类型、测试、产物一致性
npm ci && npm run all

# ② 对着 mock 上游跑完整条链 —— **绝不碰真账号**，也不需要你的凭据
./scripts/e2e-mock.sh <面板可执行文件> 18900
```

`e2e-mock.sh` 会起 mock 上游 + 一个面板实例，把上游指向 mock、导入一份假会话，
然后逐条跑任务，断言：query 逐字节、备份好礼两步、签到三段式（含回查）、
翻倍门槛、逐条领取、只领一次、**口令池的三条口径**（抓到进池 / 30 分钟窗口内不再抓 /
够 2 条有效就停止抓取）、**门的三步**（正好四发、顺序固定、两个页签都查、去重、
日程与「下一场」落池、凭据不回显）—— 以及 **mock 侧的状态真的变了**
（todaySigned / curMonthBackupSignAccept / receiveList / backupCanReceive）。
它和你跑的是**同一份脚本**，CI 里跑的也是这一份。

## 两个结构上的选择（以及一个已经打通的前提）

`mcloud` 的任务多（20 条），所以迟早要回答两个问题：

**① 怎么分组？** 面板只是"插件 → 任务"两层，没有分组概念。三条路：

| 做法 | 代价 |
|---|---|
| **一个插件 + 分组界面**（推荐先走这条） | 不用改面板；12 条任务已经在一个插件里、共用会话与状态，分组只是**显示与操作**的组织方式。分组模型已经写好了：`src/mcloud/groups.ts`（按**风险与依赖**分组，不是按功能名），接口 `GET /plugins/mcloud/api/groups` |
| 一个组一个插件（`mcloud-signin.js`…） | 每组能单独启停 ✓，但每组各有一份代码与一个 QuickJS 上下文，内存按组数乘 |
| 面板侧加「组」概念 | 最干净，但要改面板（jobs 加 group 字段 + 界面），且不只为本插件服务 |

分组维度**照 mcloud 自己的任务清单来**（类型 / 副作用 / 依赖 / 批量 / 隐藏 / 错过），
不自己发明 —— 操作一条任务前，人真正要知道的是「它安不安全、要哪种凭据」。

**② 能不能"一份 core、插件 import 函数"？** —— **现在能了**。
面板的模块加载器原先只认 `host-api`，相对 `import` 一律失败（而报错文案还建议你用它，
见 [`docs/findings.md`](docs/findings.md) F-008）。这条已经修好并验证：

```js
// plugins/js/mcloud-signin.js
import { runSign, runReceive } from './lib/signin.js';   // ← 模块放子目录
import { log } from 'host-api';
```

* 模块标识是 `file://` URL（`import.meta.url` 可用）、活绑定、循环导入、动态 import 都成立
* 扩展名可省、目录自动找 `index.js`（**放宽**，不是浏览器 ESM 的行为 —— 代价见
  [`docs/findings.md`](docs/findings.md) F-008）
* **同一份 core 被多个插件 import 只加载一次**（按 URL 缓存）——
  这是省内存的关键：不必为了共用 core 而接受 N 份打包产物
* 另有够用的 `require`（CJS 兼容）：`require('host-api')`、`require('./lib/x.js')`，
  按 CJS 规矩解析（可省扩展名），读 ES 模块时会明确告诉你「该用 import」

也就是说：**先按①的第一条走（一个插件 + 分组），需要拆的时候②那条路已经开了。**

## 拆分方案（已定）

按**功能族**拆，前缀都用 `mcloud`（起名即分组）：

| 族 | 包含 | 现在能做的 |
|---|---|---|
| `mcloud-signin` | 签到族 + **`app-task` 等每日/月默认任务** | 签到那 8 条已完；`app-task` 的**只读半边**（`app-task-matrix`）可做 |
| `mcloud-exchange` | 兑换 | **只读半边**可做（读清单 + 判"能不能兑"，不碰余额/滑块/下单）|
| `mcloud-live` | 直播 | **两半都做了**：只读那半（`live-room`，抓公开主页 + 口令输入口，不需要凭据）＋ 写那半（`live-draw`，六步链领小红花，**默认关**）|
| `mcloud-session` | 会话 | **插件现在能自己换票**：贴一份**原生凭据**（`Basic base64("mobile:号:token")`，就是 mcloud 的 `auth.raw`），`session-refresh` 自己走三步换成 H5 的 `jwttoken`，并按 100 分钟自动续（票新鲜时一个请求都不发）。ⓘ **两个族都在真账号上实测通过了**，见 `docs/findings.md` F-015 |

三族各自"写的那半"卡在不同东西上：`app-task` 会往网盘传文件且 `task/click`
不可回滚；`exchange` 下单要过滑块（而滑块接口计失败次数）；`live-room` 的
**口令本身要人给**（主播发在弹幕/小红书里，那边**无法鉴权** ⇒ 没法自动取）
—— 所以它缺的不是 WS，是**一个输入口**，而那个口已经做了。
`live-draw` 是这一族里唯一会**记账**的动作，但同口令重领回 `200112` ⇒ 基本幂等。
**先把能照实写的写完**，写的那半等证据或真账号。

## 起名即分组

面板把插件按**名字里第一个 `-` / `_` 之前那段**归拢显示（`mcloud-*` 一组、
`bilibili-*` 一组），每组带「全部重载 / 全部启用」。

所以将来把这个插件拆成几个时（比如 `mcloud-signin` / `mcloud-receive`），
**前缀都用 `mcloud`** —— 面板上它们就会聚成一块，而不是散成一排。
同理，别的项目（bilibili 之类）用它们自己的前缀。

## 装到你自己的面板上

```bash
# 面板的插件目录指向本仓库的 plugins/（一个静态二进制 + 一个目录，没有依赖）
PLUGINS_DIR=/path/to/mcloud-plugin/plugins PANEL_TOKEN=<你的令牌> <面板二进制>
```

装好后：

* 面板里能看到 `mcloud`，12 条任务全部登记
* 接口文档（导入会话、看状态、指到 mock）：[`docs/howto-session.md`](docs/howto-session.md)
* 任务挂在**白天每 15 分钟**（不是"每天 8:05 打一枪"）—— 低配盒子不常在线，
  8 点没开机 9 点上线照样补上；每条任务自带门槛，不需要动作时就只是一次只读检查
* 想让它立刻干活：面板上点「立即执行」，或
  `curl -X POST -H 'X-Panel-Token: <令牌>' -H 'x-panel: 1' <面板>/api/tasks/mcloud/task-list/run`

> ⚠️ 写接口（POST）必须带 `-H 'x-panel: 1'` —— 面板的防跨站请求伪造要求，
> **插件自己注册的路由同样适用**（见 [`docs/findings.md`](docs/findings.md) F-007）。

### M1 进行中：上游层（已完成的部分）

复刻自 mcloud 的 `mcloud-crypto` / `mcloud-upstream`，逐条都在测试里钉住：

| 模块 | 内容 |
|---|---|
| `src/mcloud/sign.ts` | 签名公式 `md5(salt + id + ts + nonce + other + salt)` + 两个盐值 + 未知 key 回落 1 |
| `src/mcloud/rand.ts` | UUID v4 与 nonce（**沙箱没有随机源** → `Math.random` + 计数，取舍写在文件头，见 F-005） |
| `src/mcloud/envelope.ts` | 签到族信封：`code` 数字或数字字符串都收、`msg`/`message` 两种键名、解析不出来给 **-1 而不是 0** |
| `src/mcloud/h5.ts` | H5 头画像（`activityid` 跟 marketname 走、`appversion` 四段、`jwttoken` **小写**）+ 13 个端点常量 |
| `src/mcloud/client.ts` | 可注入 transport 的调用层（插件里注入 `http_fetch`，测试里注入桩）+ cookie 解析（**`Expires` 里的逗号不能当分隔符**）+ 单次耗时预警线 1500ms |

测试 16 项，其中三条是「容易顺手优化掉」的行为：签名的 **timestamp 不做数值归一化**
（`'007'` 不等于 `'7'`）、`result` 形状不同**各写各的解析**（不写「两种都吃」的兼容）、
`jwttoken` 头名**不能被驼峰化**。

### 签到族 8 条：几条值得单独说的

| 任务 | 关键设计 |
|---|---|
| `sign` | **三段式**：问状态 → 提交 → **回查**。原实现写明「判据是 `infoV3`，不是 `startSignIn` 的响应 —— 它说没签，但紧接着 `infoV3` 已经是 `s:true` 了」。动作响应会撒谎，拿它当判据就是每天误报一次失败 |
| `receive` | **逐条独立**：`infoV3.receiveList` 入队 → 一次领一条 → 一条失败不影响其它（原实现专门有用例盯这件事）。`cloudType` 缺省是**空串**不是 0；`cloudType==1` 是延期领取走另一口端点（未实现，跳过并说明） |
| `multiple` | **门槛必须自己判**：`curMonthBackup && !curMonthBackupSignAccept` 都成立才发 —— 每月只有一次机会，「条件不成立还发是白白消耗」。门槛不成立时**一个字节都不发** |
| `revival` | **不可逆**：晚超过 2 小时就不做（任务表里它的语义是 skip 不是 catch-up）；「已领取」是**完成**不是失败（照抄原实现的两条件文案判定），靠底座新加的 `okWhenError` 接线 |
| `backup-gift` | **两步**：先问能不能领，能领才在下一次触发去领。`activityid` 是 `backupgift` 不是 `sign_in_3` |
| `notice` | **两步**：查两个槽（`taskOneInfo` / `taskTwoInfo`）→ 能领才领。三处照实说的东西：① 判据字段缺任何一个都**不参与判断**（`None` ≠ `Some(0)`，否则静默漏领）② `reward` **报不出到账数**（实拍只有 `{"code":0,"msg":"success"}`）⇒ 成败靠**下一轮回查** ③ "通知未开启"那一档**判不出来**（`noticeNeedsManual` 恒 false，就地声明为未被断言的分支）|

调度面也改了：签到族挂在**白天每 15 分钟**而不是「每天 8:05 打一枪」——
① 多步流程需要多次调用（一次调用一个请求的纪律）；② 低配盒子不常在线，
8 点没开机 9 点上线照样补上（这就是 catch-up 的意义）；③ 每步都自带门槛，
不需要动作时就只是一次只读检查。

**方法表**（`h5.ts` 的 `EP_METHOD`）值得单独提：我第一版凭「这些看着像 POST」
把 `infoV3` 写成 POST，真面板回了 **405**。查原实现后才发现签到族里
`infoV3` / `startSignIn` / `multiple` / `prizeRecord` / `cloudRecordV2` 都是 **GET**
（`infoV3` 还要 `?client=app`），只有 `receiveV3` / `receiveRevivalReward` /
`taskListV3` 是 POST。这条已经固化成代码里的表，下一条任务照着抄。

## 已经压出来的两条（面板侧，待修）

- **F-001 手动触发的 `lateMs` 是负数、`scheduledAt` 指向未来** —— 根因在
  `src/engine.rs:1832`：payload 里取的是任务结构里的 `next_fire`，手动触发时它还在未来。
  这条会直接污染「调度精度」统计（而手动触发是用户常有动作）。插件侧已绕开
  （负延迟单独计数、不进分布），面板侧建议在 payload 里加 `manual: true`。
- **F-002 启动时打「插件目录里没有找到任何 .js / .py 插件」** —— 根因在
  `src/engine.rs:767`：条件是 `plugins.is_empty()`，判断的其实是「**这个 worker**
  名下没有插件」。`ENGINE_WORKERS=2` 而只有一个插件时，worker 1 必然报一次。
  文案与事实不符，会让人去找不存在的问题。

## 零之二、开工前核出来的三件事（实测，不是推测）

1. **执行预算默认只有 2000 ms**（`src/engine.rs:58` `DEFAULT_EXEC_BUDGET_MS = 2_000`），
   可以用 `EXEC_BUDGET_MS` 覆盖。
   而 `http_fetch` 是**同步阻塞**的 —— 关键问题在这里：**预算打断不了正在阻塞的宿主调用**。
   QuickJS 的 interrupt handler 只在 JS 字节码边界被检查，所以一个 5 秒的请求会**跑完**，
   然后 JS 恢复执行的那一刻才被判定超时 → **上游动作已经发生，任务却报超时**
   （对「领取」类任务意味着「领到了但显示失败」）。
   → 这条单独就够回面板改一轮，所以架构上先绕开：**一次调用只做一个逻辑步骤**（见下）。
2. **cron 用的是本机 `Local` 时间**（`src/scheduler.rs` 全程 `DateTime<Local>`），
   所以「每天 8 点」在本机时区正确的前提下是对的；缺的只是 mcloud 那种**按任务指定时区**。
   （我之前把这条说重了，这里更正。）
3. `http_fetch` 的 ureq agent 只设了 `timeout_global`，**没显式设重定向策略** ——
   跟着上游走 302 的行为属于 ureq 的默认值，M1 里要实测确认（不猜）。

### 由 ① 推出的架构：可恢复的步骤机

既然「一次调用做一整个流程」会被预算打断，任务就设计成**跨多次触发推进的状态机**：

- 每次 handler 调用**只做一步**（签一次名、发一个请求、写一次状态）
- 状态（cookie / 令牌 / 今天签过没 / 上一步结果）落在自己的 SQLite 表里
- 每步都**幂等可重入**：重复触发先查「今天这步做过没有」，做过就直接返回
- 这样调度压力也被真压上了：8 条任务 × 多步 × 高频触发 —— 正好是「调度精度」那个重点

这条路径还有个副作用是好的：它不依赖面板的任何改动就能跑起来，符合「先压出来再改」。

## 一、形态

- `src/`：TS 源码，模块化（多文件）
- **产物是单文件**：面板现在一个插件就是一个文件（`plugins/js/<name>.js`），
  所以 TS 源码打包成 `plugins/js/mcloud.js`；界面是 `plugins/mcloud/` 下的静态文件
  （零构建、原生 ESM —— 与面板前端同一套做法）
- 产物**零运行时依赖**：QuickJS 沙箱里没有 Node（没有 `fs`/`net`/`crypto`/npm 包），
  `host-api` 由面板的 Resolver 提供

```
mcloud-plugin/
  src/                 TS 源码（按职责分模块）
  plugins/js/mcloud.js 构建产物（单文件，提交进仓库，CI 检查是否最新）
  plugins/mcloud/      WebUI 静态文件（原生 ESM + CSS，零依赖）
  scripts/             构建、本地跑、压测驱动
  docs/findings.md     每压出一个面板边界就记一条（数 + 根因 + 改了什么）
  docs/tasks.md        20 条任务在本插件里的实现状态与依据
```

## 一点五、规模（决定了怎么切）

`asunajs/mcloud` 现在（提交 `HEAD`，实测）：

| 部分 | 行数 |
|---|---|
| Rust 源码 `crates/`（不含 target） | **140,770** |
| WebUI `web/src`（TS） | 23,633 |
| 文档 `docs/*.md`（30 篇） | 5,632 |

按 crate 分：`mcloud-upstream` 38,055（上游 API 客户端层）· `mcloud-tasks` 36,367（20 条任务 + 内联测试）·
`mcloud-server` 25,764（路由 / CLI / 登录）· `mcloud-app` 14,870（含 `notify.rs` 3,444）·
`mcloud-core` 10,113 · `mcloud-engine` 6,481（调度）· `mcloud-store` 5,133 · `mcloud-crypto` 3,987。

**结论：全量对齐不现实。** 这些 Rust 里相当一部分是 serde 结构体、错误 enum、内联测试；
换成 JS 大概能压到 **1/3～1/2**，也就是全功能 ≈ **2.5～4 万行 JS** —— 那是个长跑。

所以这条路必须是**先切片**：核心切片（登录 + 签名 + 5 条只读任务 + 3 页界面 + 日志 + 通知）
大约 **3～5 千行** —— 而这个体量**已经足以把面板的边界全压出来**（20 条任务的调度压力来自
任务数量与频率，不是任务种类；慢任务、内存、热更新、DB 争用这几条，切片一样能压）。
先拿到数、先修面板，再决定要不要往下铺。

## 二、mcloud → 插件的能力映射

| mcloud（Rust） | 插件形态 | 现在行不行 |
|---|---|---|
| 20 条任务（HTTP 调上游） | `register_handler(name, fn)` ×20 + 面板建任务 | ✅ 行（缺下面那条） |
| 任务的**账号范围** | 面板任务没有参数 → handler 内部循环账号 | ⚠️ 面板缺口 |
| cron **带时区** | 面板 cron 没有时区 | ⚠️ 面板缺口 |
| **编排**（任务串链） | 插件内部状态机，或面板加编排 | 🤔 待定 |
| 管理员登录（会话 cookie） | **去掉** —— 面板本身就有鉴权，插件不该再来一层 | ✅ 简化 |
| 云盘账号登录（扫码/短信/密码/设备号） | `http_fetch` + `register_route`（扫码靠轮询） | ✅ 行 |
| SSE 实时日志 | 面板路由是「一次性返回」→ 改成轮询 `?after=<seq>` | ✅ 行（SSE 是候选改进） |
| 进程环形日志（现 200 行上限） | 插件自建日志表 + 界面读自己的表 | ✅ 行 |
| 9 种通知渠道 | `http_fetch` POST（rustls 内置根证书） | ✅ 行 |
| 10 页 WebUI | `plugins/mcloud/` 静态文件 + 路由 API | ✅ 行 |
| 配置导出/导入 | 插件表 + 路由 | ✅ 行 |
| **签名**（`mcloud-sign`，Rust 侧 `mcloud-crypto` 3,987 行） | 两条路：**① 纯 JS 自带**（md5/sha/aes 各几百行，自包含、适配器也能跑，慢一点）**② 面板加 `host.crypto`**（快、原生，但是面板的新依赖） | 🤔 待拍板 |
| 上传/下载大文件 | `http_fetch` **1 MiB 上限、无流式** | ❌ 面板缺口 |

## 三、面板需要新增的能力（候选，按「这个插件压得有多狠」排序）

| # | 能力 | 为什么这个插件非要 | 量级 |
|---|---|---|---|
| 1 | `host.crypto`（md5/sha1/sha256/hmac/base64/hex/random） | 上游签名没它做不了 | 小 |
| 2 | **任务参数**（面板建的任务带 payload） | 多账号要「同一个任务 × N 个账号」 | 中 |
| 3 | **长任务不阻塞引擎线程** | 现在 `http_fetch` 同步阻塞，且执行预算会打断长任务；一次上传/一次直播轮询就是几十秒 | **大（最值钱的一刀）** |
| 4 | 大 body / 流式（下载上传） | 1 MiB 上限 | 中 |
| 5 | cron 时区 | 「每天 8 点签到」是明确的时区语义 | 小 |
| 6 | SSE / 流式响应 | 实时日志、扫码 | 中（可先用轮询绕） |
| 7 | 密钥落库（云盘账号 cookie / 密码） | #1 到位后加密存，不再明文 | 小 |
| 8 | 多文件插件 | 若单文件打包用起来别扭 | 中（能不做得不做） |

## 四、测试与优化议程

| 面板边界 | 用插件的哪一块压 | 看什么数 |
|---|---|---|
| 调度精度 | 20 条任务 + 一个高频 tick | `lateMs` 的 p50 / p99 |
| 慢任务拖住同轮 | 一个大任务（1000 次串行 http）+ 一个 1s 任务 | 后者的 `lateMs` 分布 |
| 内存 < 10 MB | 跑满 20 条任务 + 热更新几十次 | RSS 曲线、有没有泄漏 |
| SQLite 无连接池 | 多任务并发写 + 大结果集 | 「database is locked」、耗时 |
| 热更新稳定性 | 任务在跑时改文件 N 次 | 旧任务残留、内存、日志 |
| 日志环形 200 行 | 短时间打 1 万行 | 丢弃计数、界面卡不卡 |
| 插件 WebUI 能力 | 10 页 SPA + 图表 | 首屏、路由、鉴权 |
| 错误隔离 | 20 条任务全抛异常 | 面板是否被刷屏/卡住 |

## 五、分期（每期都能独立跑起来）

- **M0 骨架**：构建（TS→单文件）、CI（在 Node/CPython 适配器上跑通一个 handler）、文档
- **M1 上游客户端层**：登录 / 签名 / cookie 轮换 + **mock 上游**（CI 不碰真账号）
- **M2 任务层**：20 条任务 —— **先做那几条纯只读的**（`task-list`、`prizes`、
  `cloud-snapshot`、`app-task-matrix`、`exchange-list`、`live-room`：只拉读数、不改上游账本）
- **M3 状态与日志**：SQLite 表 + 运行日志 + 轮询
- **M4 WebUI**：10 页（先总览 / 账号 / 任务 / 日志）
- **M5 通知 + 编排 + 配置导入导出**
- **M6 压力与优化**：把 `docs/findings.md` 里的边界逐条压一遍，回面板改一轮

## 六、文档与安全

- **上游账号不是测试资源**：CI 全程只打 mock；真账号只在本地手工验，且**优先只读任务**
- `exchange`（花真 AI豆、上游无幂等键）在插件里**默认关闭**，要显式开启并二次确认
- 账号 cookie / 密码不进日志、不进导出文件（导出只带配置，不带凭据）
