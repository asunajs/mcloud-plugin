# mcloud-plugin

把 [mcloud](https://github.com/asunajs/mcloud)（中国移动云盘的 Rust 自动化服务）**用 JS/TS 重写一份**，
作为 [rust-plugin-panel](https://github.com/asunajs/panel) 的插件跑起来。

两个目标**同等重要**：

1. **功能**：mcloud 的任务与界面在插件形态下真的能用
2. **压力与优化**：它是这个面板能碰到的最大的东西 —— 用它把面板的边界压出来，
   每压出一个就回面板仓库修掉，并在 [`docs/findings.md`](docs/findings.md) 记下
   「怎么测的、什么数、改了什么」

> **状态：已定稿，未开工**（等一句「开动」）。决策见下。

## 零、已定的决策

| 项 | 决定 |
|---|---|
| 仓库 | `asunajs/mcloud-plugin`（就用这个） |
| 源码形态 | TS 源码 + **esbuild 打包成单文件**（dev 依赖，产物零依赖） |
| 第一批任务 | **签到族 8 条**：`sign` `receive` `multiple` `backup-gift` `revival` `prizes` `cloud-snapshot` `task-list` |
| 上游验证 | **真账号手工验 + mock 进 CI**（CI 永不碰真账号） |
| 面板侧改动 | **先压出来再改** —— 本轮只用面板现有能力，拿到数据再动面板 |
| 签名 | **纯 JS 自带**（md5/sha/aes 自己写，插件自包含） |
| 优化重点 | **内存 10 MB** · **调度精度** · **插件 WebUI 能力** |

## 零之二、开工前核出来的三件事（实测，不是推测）

1. **执行预算默认只有 2000 ms**（`src/engine.rs:58` `DEFAULT_EXEC_BUDGET_MS = 2_000`），
   可以用 `EXEC_BUDGET_MS` 覆盖。
   而 `http_fetch` 是**同步阻塞**的 —— 关键问题在这里：**预算打断不了正在阻塞的宿主调用**。
   QuickJS 的 interrupt handler 只在 JS 字节码边界被检查，所以一个 5 秒的请求会**跑完**，
   然后 JS 恢复执行的那一刻才被判定超时 → **上游动作已经发生，任务却报超时**
   （对「领取」类任务意味着「领到了但显示失败」）。
   → 这条单独就够回面板改一轮，所以架构上先绕开：**一次调用只做一个逻辑步骤**（见下）。
2. **cron 用的是本机 `Local` 时间**（`src/scheduler.rs` 全程 `DateTime<Local>`），
   所以「每天 8 点」在本机时区正确的前提下是对的；缺的只是 mcloud 那种**按任务指定时区**。
   （我之前把这条说重了，这里更正。）
3. `http_fetch` 的 ureq agent 只设了 `timeout_global`，**没显式设重定向策略** ——
   跟着上游走 302 的行为属于 ureq 的默认值，M1 里要实测确认（不猜）。

### 由 ① 推出的架构：可恢复的步骤机

既然「一次调用做一整个流程」会被预算打断，任务就设计成**跨多次触发推进的状态机**：

- 每次 handler 调用**只做一步**（签一次名、发一个请求、写一次状态）
- 状态（cookie / 令牌 / 今天签过没 / 上一步结果）落在自己的 SQLite 表里
- 每步都**幂等可重入**：重复触发先查「今天这步做过没有」，做过就直接返回
- 这样调度压力也被真压上了：8 条任务 × 多步 × 高频触发 —— 正好是「调度精度」那个重点

这条路径还有个副作用是好的：它不依赖面板的任何改动就能跑起来，符合「先压出来再改」。

## 一、形态

- `src/`：TS 源码，模块化（多文件）
- **产物是单文件**：面板现在一个插件就是一个文件（`plugins/js/<name>.js`），
  所以 TS 源码打包成 `plugins/js/mcloud.js`；界面是 `plugins/mcloud/` 下的静态文件
  （零构建、原生 ESM —— 与面板前端同一套做法）
- 产物**零运行时依赖**：QuickJS 沙箱里没有 Node（没有 `fs`/`net`/`crypto`/npm 包），
  `host-api` 由面板的 Resolver 提供

```
mcloud-plugin/
  src/                 TS 源码（按职责分模块）
  plugins/js/mcloud.js 构建产物（单文件，提交进仓库，CI 检查是否最新）
  plugins/mcloud/      WebUI 静态文件（原生 ESM + CSS，零依赖）
  scripts/             构建、本地跑、压测驱动
  docs/findings.md     每压出一个面板边界就记一条（数 + 根因 + 改了什么）
  docs/tasks.md        20 条任务在本插件里的实现状态与依据
```

## 一点五、规模（决定了怎么切）

`asunajs/mcloud` 现在（提交 `HEAD`，实测）：

| 部分 | 行数 |
|---|---|
| Rust 源码 `crates/`（不含 target） | **140,770** |
| WebUI `web/src`（TS） | 23,633 |
| 文档 `docs/*.md`（30 篇） | 5,632 |

按 crate 分：`mcloud-upstream` 38,055（上游 API 客户端层）· `mcloud-tasks` 36,367（20 条任务 + 内联测试）·
`mcloud-server` 25,764（路由 / CLI / 登录）· `mcloud-app` 14,870（含 `notify.rs` 3,444）·
`mcloud-core` 10,113 · `mcloud-engine` 6,481（调度）· `mcloud-store` 5,133 · `mcloud-crypto` 3,987。

**结论：全量对齐不现实。** 这些 Rust 里相当一部分是 serde 结构体、错误 enum、内联测试；
换成 JS 大概能压到 **1/3～1/2**，也就是全功能 ≈ **2.5～4 万行 JS** —— 那是个长跑。

所以这条路必须是**先切片**：核心切片（登录 + 签名 + 5 条只读任务 + 3 页界面 + 日志 + 通知）
大约 **3～5 千行** —— 而这个体量**已经足以把面板的边界全压出来**（20 条任务的调度压力来自
任务数量与频率，不是任务种类；慢任务、内存、热更新、DB 争用这几条，切片一样能压）。
先拿到数、先修面板，再决定要不要往下铺。

## 二、mcloud → 插件的能力映射

| mcloud（Rust） | 插件形态 | 现在行不行 |
|---|---|---|
| 20 条任务（HTTP 调上游） | `register_handler(name, fn)` ×20 + 面板建任务 | ✅ 行（缺下面那条） |
| 任务的**账号范围** | 面板任务没有参数 → handler 内部循环账号 | ⚠️ 面板缺口 |
| cron **带时区** | 面板 cron 没有时区 | ⚠️ 面板缺口 |
| **编排**（任务串链） | 插件内部状态机，或面板加编排 | 🤔 待定 |
| 管理员登录（会话 cookie） | **去掉** —— 面板本身就有鉴权，插件不该再来一层 | ✅ 简化 |
| 云盘账号登录（扫码/短信/密码/设备号） | `http_fetch` + `register_route`（扫码靠轮询） | ✅ 行 |
| SSE 实时日志 | 面板路由是「一次性返回」→ 改成轮询 `?after=<seq>` | ✅ 行（SSE 是候选改进） |
| 进程环形日志（现 200 行上限） | 插件自建日志表 + 界面读自己的表 | ✅ 行 |
| 9 种通知渠道 | `http_fetch` POST（rustls 内置根证书） | ✅ 行 |
| 10 页 WebUI | `plugins/mcloud/` 静态文件 + 路由 API | ✅ 行 |
| 配置导出/导入 | 插件表 + 路由 | ✅ 行 |
| **签名**（`mcloud-sign`，Rust 侧 `mcloud-crypto` 3,987 行） | 两条路：**① 纯 JS 自带**（md5/sha/aes 各几百行，自包含、适配器也能跑，慢一点）**② 面板加 `host.crypto`**（快、原生，但是面板的新依赖） | 🤔 待拍板 |
| 上传/下载大文件 | `http_fetch` **1 MiB 上限、无流式** | ❌ 面板缺口 |

## 三、面板需要新增的能力（候选，按「这个插件压得有多狠」排序）

| # | 能力 | 为什么这个插件非要 | 量级 |
|---|---|---|---|
| 1 | `host.crypto`（md5/sha1/sha256/hmac/base64/hex/random） | 上游签名没它做不了 | 小 |
| 2 | **任务参数**（面板建的任务带 payload） | 多账号要「同一个任务 × N 个账号」 | 中 |
| 3 | **长任务不阻塞引擎线程** | 现在 `http_fetch` 同步阻塞，且执行预算会打断长任务；一次上传/一次直播轮询就是几十秒 | **大（最值钱的一刀）** |
| 4 | 大 body / 流式（下载上传） | 1 MiB 上限 | 中 |
| 5 | cron 时区 | 「每天 8 点签到」是明确的时区语义 | 小 |
| 6 | SSE / 流式响应 | 实时日志、扫码 | 中（可先用轮询绕） |
| 7 | 密钥落库（云盘账号 cookie / 密码） | #1 到位后加密存，不再明文 | 小 |
| 8 | 多文件插件 | 若单文件打包用起来别扭 | 中（能不做得不做） |

## 四、测试与优化议程

| 面板边界 | 用插件的哪一块压 | 看什么数 |
|---|---|---|
| 调度精度 | 20 条任务 + 一个高频 tick | `lateMs` 的 p50 / p99 |
| 慢任务拖住同轮 | 一个大任务（1000 次串行 http）+ 一个 1s 任务 | 后者的 `lateMs` 分布 |
| 内存 < 10 MB | 跑满 20 条任务 + 热更新几十次 | RSS 曲线、有没有泄漏 |
| SQLite 无连接池 | 多任务并发写 + 大结果集 | 「database is locked」、耗时 |
| 热更新稳定性 | 任务在跑时改文件 N 次 | 旧任务残留、内存、日志 |
| 日志环形 200 行 | 短时间打 1 万行 | 丢弃计数、界面卡不卡 |
| 插件 WebUI 能力 | 10 页 SPA + 图表 | 首屏、路由、鉴权 |
| 错误隔离 | 20 条任务全抛异常 | 面板是否被刷屏/卡住 |

## 五、分期（每期都能独立跑起来）

- **M0 骨架**：构建（TS→单文件）、CI（在 Node/CPython 适配器上跑通一个 handler）、文档
- **M1 上游客户端层**：登录 / 签名 / cookie 轮换 + **mock 上游**（CI 不碰真账号）
- **M2 任务层**：20 条任务 —— **先做那 5 条纯只读的**（`task-list`、`prizes`、
  `cloud-snapshot`、`app-task-matrix`、`play-ai-special`：只拉读数、不改上游账本）
- **M3 状态与日志**：SQLite 表 + 运行日志 + 轮询
- **M4 WebUI**：10 页（先总览 / 账号 / 任务 / 日志）
- **M5 通知 + 编排 + 配置导入导出**
- **M6 压力与优化**：把 `docs/findings.md` 里的边界逐条压一遍，回面板改一轮

## 六、文档与安全

- **上游账号不是测试资源**：CI 全程只打 mock；真账号只在本地手工验，且**优先只读任务**
- `exchange`（花真 AI豆、上游无幂等键）在插件里**默认关闭**，要显式开启并二次确认
- 账号 cookie / 密码不进日志、不进导出文件（导出只带配置，不带凭据）
