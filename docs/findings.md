## F-001 手动触发时 `lateMs` 是负数、`scheduledAt` 指向未来

**怎么发现的**：插件第一次跑起来，在真面板上点「立即执行」跑 `selftest`，
插件把它记进了自己的 `runs` 表 —— 表里 `late_ms = -290918`。
负数延迟不是「迟到」，是公式用错了时刻。

**证据**（面板 `PLUGINS_DIR` 指向本仓库 `plugins/`，手动触发 `selftest`）：

```
[18:42:40] [mcloud] 已注册任务 `selftest`（@every 5m），下次触发 2026-10-13 18:47:40.950
[18:42:50] [mcloud] 自检通过（6/6 通过）· lateMs=-290918
```

`-290918 ms ≈ -4.84 分钟`，正好等于「18:47:40 的下次触发」减「18:42:50 的实际时刻」。
同一条记录在 `runs` 表里：`('selftest', 1, -290918, 1, '6/6 通过')`。

**面板侧根因**（`src/engine.rs:1822-1832`）：

```rust
let (plugin, name, expr, scheduled, runs_before) = {
    let t = &sched.tasks()[idx];
    (…, t.next_fire, t.runs)          // ← scheduled 取的是 next_fire
};
let late_ms = (now - scheduled).num_milliseconds();
```

定时触发时 `next_fire` 刚好是「这一刻本来该触发的时间」，`now - scheduled >= 0` ✓。
但**手动触发**（`POST /api/tasks/{plugin}/{name}/run`）时这个任务还没到点，
`next_fire` 在未来 → 差值必然是负的，`scheduledAt` 也成了未来的时刻。

**影响**：

- 任何「立即执行」都往数据里灌一条假样本。插件要拿 `lateMs` 做调度精度统计，
  手动触发的次数越多，分布被拉得越偏 —— 而这恰好是本轮要测的重点
- 对插件作者来说，`payload.scheduledAt` 在手动触发时**是错的**（未来时刻），
  按它做判断会出错
- 界面上「立即执行」是个正常功能，用户会经常用，所以这不是边角路径

**插件侧怎么绕**（本轮）：`store.lateStats` 只统计 `late_ms >= 0` 的样本，
并把被排除的条数一起报出来（不静默丢数据）；`recordRun` 对负值在 `note` 里标记。

**建议怎么修**（面板侧，下一轮）：手动触发不是「晚到」，它没有计划时刻可言。
两种改法里倾向后者：

1. `scheduledAt = firedAt`、`lateMs = 0` —— 最小改动，但同样把「手动」混进了调度样本
2. **payload 里加 `manual: true`**，`scheduledAt = firedAt`、`lateMs = 0` ——
   插件能明确区分，统计天然干净；代价是 payload 形状变了（要同步 `docs/host-api.md`
   与两个适配器）

**状态**：待修（面板侧）。插件侧已绕开。

## F-002 启动时打印「插件目录里没有找到任何 .js / .py 插件」，但目录里明明有

**怎么发现的**：把 `PLUGINS_DIR` 指向本仓库 `plugins/` 起面板，启动日志里出现这条
`warn`，紧接着两行之后就是「mcloud 插件已加载」。

**证据**：

```
[18:42:40] [kernel] [warn] 插件目录 /Users/catlair/mobile/workspace/mcloud-plugin/plugins 里没有找到任何 .js / .py 插件
[18:42:40] [mcloud] [info] mcloud 插件已加载（M0：自检 + 调度健康；上游任务在 M1/M2）
```

**面板侧根因**（`src/engine.rs:762-771`）：这条警告在**每个 worker 的启动路径**上，
条件是 `plugins.is_empty()` —— 即「**这个 worker** 名下一个插件都没有」。
`ENGINE_WORKERS=2` 而只有一个插件时，worker 1 必然是空的，于是每次启动都报一次。

`plugins.is_empty()` 判断的其实是「本 worker 分到的插件集为空」，
而文案说的是「插件目录里没有插件」—— 两件不同的事。

**影响**：运维排障时会被误导去找一个不存在的问题（目录明明有插件）。
日志是这个项目的重要事实来源，错的警告比没有警告更贵。

**插件侧怎么绕**：无（纯面板日志问题）。本轮只记录。

**建议怎么修**（面板侧，下一轮）：两种改法：

1. 只在**所有** worker 的插件集都为空时报警告（把「全局为空」和「本 worker 为空」分开）
2. 本 worker 为空时降级成 `debug` 级、且文案改成「worker N 未分到插件（共 M 个文件）」

倾向 2：`ENGINE_WORKERS=2` + 单插件是正常状态，不该是 `warn`。

**状态**：待修（面板侧）。

## F-003 `/api/state` 无法区分「没有插件」和「还没装完」

**怎么发现的**：本仓库 CI 的 E2E 第一次跑就红了，报「没有加载 mcloud 插件，只有 `[]`」——
但同一份面板日志里明明写着「已加载 1 个插件、2 个调度任务」。时间戳对得死死的：

```
10:47:22.34  我的断言跑完（state.plugins = []）
10:47:22.38  插件装好（[mcloud] 插件已加载 … 任务: 2）
```

**面板侧根因**：HTTP 服务在引擎装插件**之前**就开始响应了，而 `/api/state` 的
`plugins` 在那段时间里是空数组 —— 调用方无法区分「这个配置下真没有插件」和
「还在装」。脚本（包括本仓库的 CI、面板自己的冒烟）只能靠轮询「等到出现为止」。

**影响**：任何「起面板→立刻查状态」的自动化都会偶发拿到空列表。
这一类错在现场表现为「**有时**插件没加载」——很难复现，也容易被归咎于插件本身。

**插件侧怎么绕**：CI 里等的是「插件带着任务出现」，不是「接口返回 200」。

**建议怎么修**（面板侧，下一轮）：`/api/state` 暴露一个就绪标志，例如
`"engine": {"loaded": true, "plugins_loaded": 1, "plugins_scanned": 1}`，
或者在启动完成前让 `/api/state` 返回 503。前者对轮询更友好（也不破坏既有字段）。

**状态**：待修（面板侧）。

## F-004 `tasks` 与 `jobs` 语义不同，字段名不提示

**怎么发现的**：本仓库 CI 写断言时，把任务名去 `/api/state` 的 **`tasks`** 里找
（看名字以为是「所有任务」），结果拿到 `[]`。实际形状：

```
/api/state
  plugins[]  →  { name, runtime, tasks: 2, ticks, has_ui, has_on_tick, error … }
                                                     ↑ 这里是**数量**，不是列表
  tasks[]    →  只有正在跑的调用（样例里只有 kernel 自己的 heartbeat）
  jobs[]     →  **任务定义**在这里：{ plugin, name, next_run, last_run, deleted, last_error … }
```

**影响**：本仓库是这套 API 的**第一个外部消费者**，两次断言都栽在这里
（第一次 `p['tasks']` 拿到 int 2 → TypeError；第二次按 `tasks` 过滤拿不到任务）。
对插件作者来说这是纯摩擦：名字不提示区别，而猜错的代价是一轮 CI。

**插件侧怎么绕**：CI 改用 `jobs` 并按 `plugin` 过滤。

**建议怎么修**（面板侧，下一轮）：不一定要改名（改名是破坏性的），
在 `/api/state` 的字段注释 / `docs` 里写清「`tasks` = 正在跑的调用，`jobs` = 任务定义」，
或者把 `tasks` 改成 `inflight`（语义更准）。这条优先度低 —— 但它是**第一个外部消费者
真实的踩坑记录**，值得留下。

**状态**：待定（面板侧，属于文档/命名的摩擦，不是 bug）。

## F-005 插件沙箱里没有任何随机源

**怎么发现的**：M1 复刻上游签名时，`x-request-id` 与 `x-nonce` 在原实现里是
`uuid::Uuid::new_v4()`（172 位随机）。翻遍宿主 API 的最小公共子集，
没有任何一处能拿到随机字节：没有 `crypto`、没有 `crypto.getRandomValues`、
没有 `host.random` —— 只有 `Math.random()`。

**影响**：

- 本插件这一层**可以接受**（诚实写在 `src/mcloud/rand.ts` 的文件头）：
  `x-request-id` 只要求唯一；`x-nonce` 是防重放用的，但签名盐**写死在客户端里**，
  真正的凭据是 cookie / jwttoken —— 猜中 nonce 并不能伪造签名
- 但这是面板侧的一个**真实能力缺口**：生成密钥、一次性口令、抽签、幂等 ID
  这类插件做不了。而且「用 `Math.random()` 顶上」这种写法会悄悄扩散 ——
  每个插件作者都会踩一遍，然后各自写一句「这里够用」的注释

**插件侧怎么绕**：`Math.random()` + `Date.now()` + 自增计数（保证同毫秒内不重复），
并把强度取舍写在文件头。

**建议怎么修**（面板侧，下一轮）：加 `host.random(n) -> string`（宿主侧用现成的
`getrandom`，返回 hex 或 base64）。这是**小改动、明确的能力缺口**：
宿主已经依赖了 `getrandom`（令牌盐就是它生成的）。

**状态**：待修（面板侧）。

## F-006 宿主 `http_fetch` 失败时的返回形状与文档不一致，而且**长得像正常结果**

**怎么发现的**：在真面板里导入会话 → 插件内部发一次上游请求（假凭据，注定失败）→
路由返回 500，错误是：

```
TypeError: cannot read property 'length' of undefined
    at callOnce (mcloud.js:591:15)
```

**面板侧实际行为**（读源码确认）：

```rust
// src/jshost.rs
match state_for_http.do_http_fetch(&url, &opts) {
    Ok(s)  => s,
    Err(e) => json_error(&e),          // → {"error": "…"}
}
```

也就是说失败时返回的是 `{"error": "…"}` —— **没有** `status` / `headers` / `body`。
而 `docs/host-api.md` 只写了成功形状（`→ { "status": int, "headers": {…}, "body": str }`），
没写失败形状。

**为什么这条比一般的「文档不全」更坑**：

1. 返回的对象**长得像一个正常结果**。任何写 `res.body` 的代码会拿到
   `TypeError: cannot read property 'length' of undefined` ——
   报错位置在**插件里**，看起来像插件自己的 bug。我第一反应也是去翻自己的 `callOnce`。
2. 它**只在真面板里出现**。Node 测试里的桩是我自己写的，形状当然"正确" ——
   也就是说：你越是只在 Node 里测，越测不到它。
3. 我自己写的那份 `src/host-api.d.ts` 把它声明成了纯 `FetchResult`，
   于是 **TypeScript 没有机会提醒我** —— 一个写错的 `.d.ts` 会悄悄拿走类型安全。

**插件侧怎么绕**：`callOnce` 先认形状（`error` 字段 / `body` 不是字符串 / 干脆是
`undefined`），再取字段；三种都变成「可读的失败」而不是异常。
测试里补了三条用例，桩**故意造出**失败形状与畸形形状。

**建议怎么修**（面板侧，下一轮，二选一）：

- **推荐**：`docs/host-api.md` 里把失败形状写进返回签名 ——
  `-> { "status", "headers", "body" } | { "error" }`，并加一句
  「失败时**没有** `status`/`headers`/`body`，不要直接读 `res.body`」
- 更彻底：成功/失败都带 `ok` 字段（`{"ok":true,status,headers,body}` /
  `{"ok":false,error}`），调用方先看 `ok` —— 破坏性变更，需要发版说明

**顺带**：`docs/host-api.md` 的返回签名是给**插件作者**看的契约，
这类「成功一种形状、失败另一种形状」的接口，文档里应该像错误码一样列出来。

**状态**：待修（面板侧）。

## F-007 面板对写请求强制 `x-panel: 1`，**插件自己注册的路由也适用** —— 但插件文档里没提

**怎么发现的**：在真面板上用 curl 调自己插件的 `POST /plugins/mcloud/api/session`，
收到一句中文说明：

```
写接口要求请求头 `x-panel: 1`（防跨站请求伪造；面板页面自己会带上）
```

**这不是 bug** —— CSRF 防护是对的，而且这条对插件路由生效**也是对的**
（否则第三方页面就能借用户的浏览器打插件接口）。但它是**插件作者必须知道的事**：

- 插件自己的 WebUI（`plugins/<name>/**` 下的静态页）里发 POST 时**必须带上这枚头**，
  否则会失败。失败信息是人话，排查不难；但如果插件作者只看了 `docs/host-api.md`
  （那里只讲 `register_route` 的注册与请求/响应形状），就会以为「我的路由我作主」。
- 写脚本的人同样容易漏（我自己就漏了，第一轮验证白跑一次）。

**插件侧怎么绕**：在 `docs/howto-session.md` 里显式写了这一行，并说明
「插件自己注册的路由同样适用」。后面做 WebUI（M4）时，页面里的 fetch 统一包一层
自动加头。

**建议怎么修**（面板侧，下一轮，都是小改动）：

1. `docs/host-api.md` 的 `register_route` 一节加一句：写方法（POST/PUT/DELETE…）
   需要请求头 `x-panel: 1`，与面板自身接口同一套规则
2. 可选：给插件作者一个现成的 GET 出口读「本面板对写接口的要求」，
   或者在 `docs/plugins.md`（如果存在）里点一下

**状态**：待修（面板侧，文档）。低优先，但能省掉每个插件作者的一次白跑。

## F-008 相对 `import` 其实不成立，而报错文案偏偏建议你用它 ✅ **已修（面板侧）**

**怎么发现的**：想按"一份 core + 多个薄插件"来切这个项目，先写了个探针验证插件能不能
`import './lib.js'`：

```text
[probe] 插件加载失败: ReferenceError: Error loading module './lib.js':
        只内置了 `host-api` 模块；插件之间请用相对路径 import
```

**面板侧根因**（读源码确认）：

- `HostApiResolver::resolve` 把模块名**原样返回**，连 `base`（导入方路径）参数
  都标着 `_base` 没用上 —— 注释还写着"其它交给默认规则（相对路径）"，那是**意图**，
  从来没实现
- `HostApiLoader::load` 只认 `host-api`，其余一律 `Err`
- 于是"相对 import"两头都不成立，而错误文案建议的就是这件事

顺带撞出第二个问题：`plugins/js/lib.js` 这个"库文件"**自己也被当成一个插件加载**
（任务数 0）。扫描规则是"下钻两层 + 只跳过带 `index.html` 的目录"，只考虑到了
配置页资源，没想到模块目录。

**影响**：插件作者按报错提示做，会收到同一句话 —— 很容易以为自己路径写错了，
去反复检查相对路径。对"把一个大项目拆成 core + 薄插件"这种结构，等于门是关着的。

**已修**（`asunajs/panel`，commit 见仓库）：

- 解析器按 **URL 语义**把相对说明符解析成 `file://` URL（模块标识就是 URL，
  顺带 `import.meta.url` 也填上了 —— QuickJS 不自动给，得宿主填）
- 加载器按解析出的路径读文件；边界限制在插件目录内
- ESM 语义，但解析**放宽**：扩展名可省、目录自动找 `index.js`（候选链
  `原样 → +.js → +.mjs → /index.js → /index.mjs`），这条链与 `require` 共用
- 另加 `require`（CJS 兼容）：`require('host-api')`、`require('./lib/x.js')`、
  与 import 同一套解析、按 URL 缓存；读 ES 模块时明确报错「请用 import」
- 两个方向都给了能照着做的提示：`require` 读 ES 模块 → 「请用 import」；
  `import` 读 CJS 文件 → 「请用 require，或改成 ES 模块」
- 扫描规则收紧：只收 `plugins/` 根与 `plugins/js|py/` 这一层 → 「模块放子目录」
  成了结构性约定，库文件不会再变成插件

**对本仓库的意义**：`core + 薄插件` 这条路通了，而且**不复制 core** ——
同一个模块文件被多个插件 import 只加载一次（按 URL 缓存），
这对"低配盒子上跑很多插件"的内存账很关键。也意味着不必为了共用 core
而接受 N 份打包产物（esbuild 每条入口都会内联一份 ✗）。

**状态**：已修（面板侧），本仓库可开始按这个结构切分。

## F-009 · 直播口令是「实例级共享池」，且有一处**刻意分叉**的判据

读源码时发现的（还没实现，先把事实钉住）。

**口令（弹幕里那串东西）是全实例共享的资源**：任何账号拿到一条，别的账号、别的
mcloud 用户都能拿它去领小红花。所以原项目把它提升到「实例级、跨用户、跨重启」的池，
三条口径是用户定的：

1. **按周期划界**：5 小时 TTL 兜底（与旧 TS 的 `SHARED_KOULING_TTL` 同值），
   另外「开播判定门」关上后再等一段就**封场**。为什么不用自然日：直播会跨零点，
   按日切会把一场直播从中间劈开，后半场又要重新抓一遍 —— 正是这层要消灭的事。
2. **够 2 条有效就全场停止抓取**。
3. **过期视同无效**（行为上不可复用），但**原因留着** —— 界面上要能看出
   「这条是口令错还是过期了」，那对判断上游什么时候作废口令有用。

### ⚠ 一处刻意分开的判据（改动前务必读完）

`200118`（**过期**）在池里算 **无效** ✓；但任务层有一条**相反的**规矩：
`rejected_kouling()` 对 `200118` 必须返回 `false`，否则会触发一次**毫无意义的 60 秒重听**。

**这不是矛盾**，是两个不同的问题：

| 谁在问 | 问的是什么 | 答案 |
|---|---|---|
| 池 | 「这条口令还能不能再拿去用」| 过期了就不能 ⇒ **无效** |
| 重听 | 「我是不是把口令**认错**了」| 过期说明我认得没错 ⇒ **不重听** |

源码原话：谁把这两处合并成一处，就会得到「要么不停地重听、要么拿着过期口令反复投」。

### 入口点（下一步从这儿进）

| 位置 | 是什么 |
|---|---|
| `crates/mcloud-core/src/kouling.rs` | 口令池（三条口径、`normalize`、`ClaimVerdict`）|
| `crates/mcloud-core/src/live_auto.rs` | 自动那条（还没细读）|
| `crates/mcloud-tasks/src/live_room.rs` | 任务层（`KoulingCollector` / 两个来源 / 抽奖）|
| `crates/mcloud-upstream/src/live_ws_client.rs` | WS 那条来源（`connect_live_ws` / `live_ws_url`）|

`kouling.rs` 只做池）。下一步先读 `live_auto.rs`。

2. 「两个来源地位相同，少一条腿不等于走不了」—— 对了一半 ✓（主页确实是一次公开 GET）

## F-010 · 小红书那一支定位到了，而且它**不需要凭据**

F-009 结尾留了一句"**还没定位到的**：小红书主页那一支的 GET URL 与解析规则"。
2026-10-13 定位完毕，并且顺带发现一件比 URL 更重要的事。

**权威源是原项目的 TS**：`mcloud-sign/packages/core/src/live-room/kouling.ts`
与 `xiaohongshu.ts`（Rust 侧 `crates/mcloud-upstream/src/live_kouling.rs` 是同一份
行为的第二次移植，它的模块文档把两处"照抄会出错"的坑记下来了）。

| 项 | 值 |
|---|---|
| 主页 URL | `https://www.xiaohongshu.com/user/profile/568caf13aed7585949773b30` |
| 请求头 | 伪装桌面 Chrome（UA / accept / accept-language / referer）——**必须逐字照抄**，见下 |
| 候选文本 | 四级：内嵌 JSON 的 `displayTitle/title/desc` → 服务端渲染元素 → `<meta content>` → 整页纯文本逐行 |
| 取值规则 | **第一条命中即返回**（主页按时间倒序 ⇒ 第一条可解析的笔记就是最新一期；继续往下找会把历史口令也交出去，而那些一律回 `200108`）|

### ⚠ 一件比 URL 更重要的事：**这条链不需要任何凭据**

主页是**公开 GET** —— 没有 cookie、没有 jwt、与云盘账号无关。
所以 `live-room`（只读那半）是**本插件第一条无凭据任务**：

- 还没导入会话的机器上，它照样有产出；
- 凭据失效时（所有签到任务**共同的**失败原因）它**不受影响** —— 而那种时候
  恰恰最需要有人告诉你"现在还剩什么是好的"。

代价是它**不能**走 `base.ts` 的 `runTask`：那个底座的第二步就是"没有会话就别打上游"，
共用底座会把这条任务挡在门外。所以它是独立的一条（`tasks/liveRoom.ts`），
只借了 `recordError` / `clearError` 两个落盘工具。

### ⚠ 另一件：**"空壳页"与"这期没发"在解析层长得一模一样**

小红书对非常规 UA 会回一个空壳页，而空壳页解出来是 `[]`，
主播这期没发也是 `[]` —— 源码里明说了这一点。**这两个结论的代价不对称**：

- 说成"这期没发" ⇒ 用户以为一切正常，而其实他的 UA 被挡了、永远抓不到；
- 说成"被挡了" ⇒ 用户去改 UA，而其实只是这期没发。

所以我**不下结论**：读数里如实报**页面大小**（`chars`，原始证据），
note 里两种可能都写出来；页面小于 5 KB 时额外给一条**标注为「猜」**的提示。
把它当判据（例如"小于阈值就报失败"）就是编造结论 —— 我没有"真实主页最小大小"的实拍样本。

### 顺带：这一块**JS 移植比 Rust 便宜**（白拿的一处）

Rust 的 `regex` 不支持前瞻，它的 `\s` 也只有 ASCII 六个（JS 的 `\s` 含全角空格
`U+3000`、NBSP、BOM）。所以 Rust 侧要手写 `JS_SPACE_CLASS` + 把带前瞻的原式改成
显式扫描，并为此踩了"扫描该推进到头还是到尾"的坑（TS 的 `g` 是非重叠的，
Go 参考实现按 `pos = headEnd` 推进会多解出一条）。

**在 JS 里这些坑根本不存在**：`\s` 就是 JS 的 `\s`，前瞻就是前瞻，
原式可以**逐字照抄**。这是"把 Rust 重写成 JS"里少见的、纯粹白拿的一处。

### 验收方式：41 条黄金向量，**不一致就改实现，不改期望值**

`test/fixtures/live-room-vectors.json`（弹幕 36 条 + 小红书 5 条）的期望值出自
**原项目 TS 源码真跑**，不是手写的。上游那份文件自己也记着一段教训：这两段
**一度**是手写期望值，结果与真实现不符 —— 手写"我觉得应该是这样"等于没测。

另有 9 条**单独立**的契约测试，钉住"看着像瑕疵、其实是契约"的地方
（假阳性 `口令是相伴什么`、无空白不切分、格式 1 与 2 同时命中、全角空格、
越界实体不炸整页）。这些地方**不要"顺手改进"**：口令是服务端当场校验的，
严过头会把**真口令**滤掉，而口令只在直播那一小时有效，**没有第二次机会**。

### 唯一一处刻意偏离原 TS（写清楚免得后人以为抄漏了）

`decodeHtmlEntities` 里的 `String.fromCodePoint`：原 TS 对越界码点（`&#1114112;`）
会抛 `RangeError` ⇒ **整次提取失败**。这里改成保留实体原文（与 Rust 侧同一取舍）。
理由是不对称：保留原文最多多一个解不出口令的候选，抛异常则会把整页的**真口令**一起丢掉。

### 已知风险（没解决，记着）

面板单次执行预算默认 2000ms，而 `http_fetch` **打断不了**（见 F-001 那一族）。
抓一次小红书主页是**一个大页面**（几百 KB），在 QuickJS 里做正则可能吃掉相当一部分预算。
好在这是**只读**动作：超时的代价是"这一次没读到读数"，没有副作用 ——
这正是"先做只读半边"的红利。真要接写的那半（领小红花），这个预算问题必须先解决。

## F-011 · 宿主 `http_fetch` 曾**覆盖插件的 User-Agent**（已修，面板侧）

**怎么发现的**：给 `live-room` 的 E2E 加了一条断言「UA 伪装在」——
第一次跑就红了：mock 收到的 `user-agent` 是 `plugin-panel/host-api`，
而插件给的是桌面 Chrome 的 UA。

**原因**（面板 `src/hostapi.rs`）：构造请求时先塞一枚默认 UA，再把插件的头
**append** 上去 ⇒ 请求里有**两枚** `user-agent`，而服务端只看第一枚。
`accept` / `referer` 这些只有插件给，所以看上去"头透传是好的"，
只有 UA 这一个静默失效。

**为什么这类错最贵**：它**不报错**。对"必须伪装 UA 才能拿到内容"的站点
（小红书：非常规 UA 会被回一个**空壳页**），而空壳页与"这期没有数据"在解析层
**分不开** ⇒ 插件会一路以为"上游没有数据"，而其实是被自己人挡住了。
换句话说：F-010 里那条"我不下结论、只报页面大小"的取舍，正是被这一条逼出来的
—— 如果当时就下结论说"这期没发"，这个 bug 会一直藏着。

**修法**（`asunajs/panel` b31c9cb）：抽出纯函数 `build_http_request`（能单测），
规矩改成**插件的头就是插件的头**，宿主只在插件**没给** `user-agent` 时才兜底；
头名按大小写不敏感比较（否则写 `User-Agent` 就绕过判据，现象一模一样）。

**教训（对写插件的人）**：宿主 API 的"透传"承诺要用**一条断言**去钉，
不能靠读文档。这次是"加了一条本来只想防回归的断言，结果它当场抓出一个真 bug"。

## F-012 · 领小红花（写那半）落地，两处是**E2E 当场抓出来的**

写那半 = 六步链：① 读余额 → ② 埋点 ×5 → ③ 首次参与惊喜奖 → ④ 逐口令 `draw`（**唯一写请求**）
→ ⑤ 复活花 → ⑥ 再读余额。一次 handler 调用只推进一步（面板预算 2000ms，见 F-001 那一族）。
开关**默认关**，界面上二次确认。

### ① 判据用 `res.ok` 会**吞掉业务结论**（单测抓到的）

`callOnce` 的 `ok` 是「HTTP 200 **且** code === 0」。而这条链上：

| 码 | 语义 | 是失败吗 |
|---|---|---|
| `200112` | 已兑换过 | **不是** —— 口令是对的 |
| `200118` | 本场已结束 | **不是** —— 口令是对的 |
| `200108` | 口令无效 | 是（唯一会触发重听的那个） |
| `200110` | 首次惊喜奖已参与过 | **不是** |

拿 `res.ok` 当门槛，这四条会被当成"失败"吞掉 ⇒ 界面上一片红，而其实该领的已经领了。
**判据改成「有没有拿到信封」（`res.env === undefined` 才是真失败）**，各步再各自看 code。

### ② ⚠ 写那半第一版**真的打到了移动的服务器**（E2E 抓到的）

两个错叠在一起，任一单独出现都不至于：

1. URL 写死在构造器里（`BASE_LIVE_ROOM_FEEDBACK`），`baseUrl` 指到 mock 对它**无效**；
2. 路径常量**漏了 `/ycloud` 前缀** —— 而 `base` 替换的是**整个源**，
   所以"指到 mock"之后会打出一个不存在的路径。

结果是本地 E2E 里那几步打到了 `https://m.mcloud.139.com/ycloud/liveRoomFeedback/user/info`。
**实际后果为零**（带的是假 jwt，被 `90001` 挡下，没碰到任何账号），但这是纪律问题：
仓库的规矩是「CI 全程只打 mock」，真机上出这种错就是**测试污染真环境**。

修法与 F-011 同一套：**让 `baseUrl` 能把这族的源整个换掉**，并加一条测试
「六步链的每一个请求都必须以 mock 的 base 开头 —— 一个字节都不许外流」。

### 那处刻意分叉的判据（F-009 提过，现在有实现与端到端证据）

`rejectedKouling()` **只有 `200108` 返回 true**；`200118` 是「本场已结束」，
既不进"口令错"那一栏、也**不触发**重听。E2E 里 mock 刻意对含「过期」的口令回 `200118`，
断言它与成功那一条走**不同**的分支 —— 这样这处分叉就不会在将来被"顺手合并"掉。

### 还没验到的（诚实标注）

**这一族的请求头形状没有在真账号上验过**。CI 只打 mock，而 mock 验的是"我发出去的形状"，
不是"上游接受它"。首次真机跑要盯 `90001`（凭据都在却过不去）——
那说明 `liveDraw.ts` 文件头记的那套头（H5 公共头，**不带**签到族的签名头与 cookie）还缺东西。

## F-013 · 拿**真实现自己的请求对象**对拍，抓到一处偏差（`user/info` 多带 content-type）

我原先在 `live_flower.rs` 的文件头给写那半标了一句"⚠ 请求头形状**没在真账号上验过**"。
验不了真账号（缺 H5 的 `jwttoken`，见 F-014），但**有一件更强的、离线就能做的事**：

> 把真实现（Rust）自己构造出来的请求逐字打出来，和插件侧**逐条对**。

做法：临时加一个 integration test，调 `live_flower::*_request()` 把 method / url /
全部 header / body 打出来（**不发任何请求**），跑完即删。

### 结果：六口里五口逐字节一致，一口不一致

一致的部分（含最容易写歪的几处）：

| 项 | 真实现 | 插件 |
|---|---|---|
| `draw` 的 query 编码 | `?code=%E4%B8%AD%E7%A7%8B%E5%8F%A3%E4%BB%A4` | 同 ✅ |
| `journaling` 的表单体 | `module=uservisit&optkeyword=…&sourceid=1007&marketName=…` | 逐字节同 ✅ |
| `give` / `draw` / `revival` 的 body | `None`（无 body、无 content-type） | `undefined` ✅ |
| 六口共用的头 | Accept / activityid / appversion / Origin / Referer / User-Agent | 同 ✅ |
| Referer 的 `targetSourceId` | `001005`（不是直播侧的 `017027`） | 同 ✅ |
| UA | iPad `18_7` 那个 | 同 ✅ |

**唯一一处偏差**：`user/info` —— 真实现**不带 content-type**，我照文档多带了一枚

⇒ 教训写在这儿：**文档与代码不一致时，代码才是实际发出去的**。

文档是二手证据，构造出来的请求才是原始证据。

不需要账号、不需要网络、几秒钟出结果，而且**比"打一枪看它成不成"更细**：
它比的是"我发的每一个字节"，不是"上游这次有没有回 0"。
凡是"插件复刻某个上游协议"的地方，都该先做一次这个对拍。

## F-014 · 「换票那一步做不了」这句话我连着说了两轮，两轮都错

**背景**：插件的会话一直只能靠人手从浏览器抄 `cookie` + `jwttoken` 贴进来。
我在 `groups.ts` 里给它记的理由是「换出该页 jwttoken 的那一步**在实拍归档里没有** ⇒ 现在做不了」。

2026-10-14 把这条链补上了（`mcloud/h5session.ts` + `sessionExchange.ts`）。
回头看，那句话错在**把"我没有"说成了"不能做"**，而且是连着两轮：

| 我说的 | 真相 |
|---|---|
| 「实拍归档里没有」 | 那是**实拍**没有；**实现**有 —— `crates/mcloud-upstream/src/session.rs` 那三百行就是它 |
| 「⇒ 现在做不了」 | 做不到的只是「照**实拍**逐字复刻」；而通用那套是照**实现**复刻的，一样能到"一行不差" |

**教训**（这条比代码值钱）：判断"能不能做"之前，先分清缺的是**哪一类**东西：

```text
缺机制（上游协议长什么样不知道）      → 真做不了，等实拍
缺参数（机制知道，这一页的取值不知道）→ 机制可以通用地做，缺的那一页单独标
缺少据                              → 只是我手上没有，不是不能有
```

这一条是**第三类**：凭据在用户手上（mcloud 的 `data/accounts.json` → `auth.raw`），
我手上没有而已。而我把"我手上没有"写成了"做不到"，于是插件白背了两轮的限制。

### 顺带修掉的另一处同源错误

`fun-ai` 那条也标着 `evidence: 'no-ticket'` —— 现在机制有了，它缺的是**它自己那一页的
换票参数**（`marketName` / `sourceId`）。签到页与 `msgpushon` 页有实拍，它没有。
⇒ 缺参数 ≠ 缺机制，两种状态的后续动作完全不同，不该用同一个词盖住。

## 这条链补上之后，插件才算真能用

之前的状态是"能不能用取决于你两小时前有没有手工贴过票" —— 而票一过期,
**所有任务一起**回 `90001 未登录`，看起来像"账号被踢了"。

现在：贴一份**原生凭据**（就是 mcloud `auth.raw` 那个形状），插件自己走三步换票，
并按 100 分钟自动续（`session-refresh`，`*/2 * * * *`，票新鲜时**一个请求都不发**）。

## F-015 · 真机实测抓到「默认 content-type」：漏了它，线上回的是**看起来像"路径不存在"的 404**

### 怎么发现的

把 F-014 那三步链实现完之后，拿 mcloud 里那份**真凭据**（`data/accounts.json`
→ `auth.raw`）在本地真跑了一次。结果：

```text
① querySpecTokenV2  HTTP 200  ✓ SSO token 42 字符
② api/timestamp     HTTP 200  ✓
③ tyrzLogin         HTTP 404  ✗ —— nginx 说路径不存在
```

`404` 是个**会把人带偏的信号**：它说"你这个地址没有这个接口"，
于是第一反应是"端点改版了"。我先探了几条路径，拿到一组很有意思的对照：

| 路径 | 方法 | 回 |
|---|---|---|
| `/ycloud/auth-service/auth/tyrzLogin` | POST（只带 content-type: application/json） | **404** |
| `/auth-service/auth/tyrzLogin` | POST | 405 |
| `/ycloud/api/timestamp` | POST | 405 |
| **`/ycloud/auth-service/auth/tyrzLogin`** | **POST + H5 全套头 + `content-type: application/json;charset=UTF-8`** | **200 `{"code":401,"msg":"请求签名校验失败"}`** |

最后一行是关键：**同一个路径，带上 content-type 就"存在"了**。
⇒ 线上网关**按 content-type 路由**，而"缺它"的表现是 404，不是 400。

### 根因：补它的是**传输层**，不是构造器

真实现里请求构造器（`live_flower::*_request` / `session::tyrz_login_request`）
**不设** content-type；补它的是 `mcloud-upstream/src/client.rs`：

```rust
fn default_content_type(req) -> Option<&'static str> {
    if !has_body(req) { return None; }                 // 无体 ⇒ 不补
    if 已有 content-type 头（大小写不敏感）{ return None; }  // 声明过 ⇒ 不覆盖
    Some("application/json;charset=UTF-8")
}
```

### 我在这件事上连着错了三轮（记下来，比结论值钱）

| 轮 | 我做的 | 错在哪 |
|---|---|---|
| ① | 按**模块文档**给 `user/info` 在**构造器**里加了 `application/json` | 位置错（该在传输层）、值也错（缺 charset）。文档那张表写着 json，而代码里没设 |
| ② | 拿真实现**构造出来的请求**对拍，把构造器里那枚**删掉了** | 对拍的是构造器 —— 而构造器本来就没有。我"验证"了一个本来就对的输出，却得出"不该有"的结论 |
| ③ | 真机实测 + 路径对照 | 才定位到"补它的是传输层" |

三轮的共同错误是同一个：**把"某一层的输出"当成了"线上发的字节"**。
构造器只是链条的第一段，后面还有传输层（补 content-type、补 UA、去重头……）。

⇒ 所以现在这条规则**放在传输层**（`main.ts` 注入的 transport 上包一层
`applyDefaultContentType`），与真实现同构 —— 散在各个构造器里就会漏，③ 就是漏的那个。

### 修完之后，真机全绿

```text
① querySpecTokenV2  HTTP 200  ✓ SSO token 42 字符
② api/timestamp     HTTP 200  ✓
③ tyrzLogin         HTTP 200  ✓ jwttoken 907 字符
④ infoV3（签到族）   HTTP 200  code:0 —— 真实账号数据
④ user/info（小红花）HTTP 200  code:0 flowerCnt 有值
```

**两个族（签到族 / 小红花族）都在真账号上验证通过了。**

## F-020 · 我**反复**把「任务的目的」当成「风险」（三次）

同一个病，犯了三次，每次换个名字：

| 次 | 我写的 | 错在哪 |
|---|---|---|
| ① | `slide.ts`："拿 0 去凑是拿**真豆去赌**" | offset 错了那一枪回 `514`，**不成交也就不扣豆** —— 代价是一次题面，不是豆。而**扣豆是成交的标志**，是目标 |
| ② | `risky` 组："**真扣 AI豆**、不可回滚" | 同上：把成交讲成亏。真正不可回滚的是**选择**（换来的是不是想要的那一件） |
| ③ | `cloud-write` 组："**会往你的网盘里写文件**……想清楚再点" | **写文件就是这个任务的内容**。上传任务不上传文件，那叫没做 |

## 一句话的口径

> **任务的定义就是改上游状态。** 上游不显示完成，那就不叫完成；
> 上传任务不上传文件，那就不叫上传。

所以"会写 / 会花 / 会改"**不是**需要请示的理由 —— 那是**载荷**，不是副作用。
需要提醒的只有一件事：**它会留下什么**（占网盘空间、少掉豆、换来的东西是不是你要的）。

## 我为什么会反复犯

因为"破坏性操作要谨慎"这条通用直觉**在这类任务上是错的**：
这里没有"只读地完成任务"这种选项。把通用直觉套上来，就会得到
"为了安全而什么都不做"——而**什么都没做**恰恰是这个插件最没用的状态。

判据应该是：**这一枪发出去有没有可能成功？**
可能 ⇒ 就发（哪怕会真的改上游）；不可能 ⇒ 不发（那是白打）。

## 落到代码上的检查项

**不是**去加"面向上游写入的确认"，而是：
· 元数据里不许把"写/花"写成风险（只写"它会留下什么"）
· 未实现的任务，`note` 里要写**真正的原因**（报文没抓全 / 缺配方参数），
  不许拿"它会写网盘"当理由 —— 那会让人以为"不做是稳妥的选择"
· 我在对话里也不该每到写操作就停下来问 —— 那是把任务的目的当成需要批准的例外

## F-021 · **抓包也会错**：它记的是"客户端发了什么"，不是"什么能成功"

`mcloud-capture` §3.6.6 有一条**明确而且看着很硬**的结论：

> H5 传的是 `{acceptDate: t.acceptDate}`，而两个真实账号的 `receiveList[]` 里**没有
> `acceptDate` 这个字段** ⇒ 值是 `undefined` ⇒ axios 把整个键丢掉 ⇒ 真实客户端发出去的
> 是 **`GET …/receiveTaskExpansion`，一个查询参数都没有**。
> ⚠ 别写成 `?acceptDate=` —— 那是**另一个请求**（多一个空参数）。

推理链每一环都对，结论也确实是"客户端发了什么"。**但那个请求是失败的。**

2026-10-14 真机实测（同一份凭据、同一个签名）：

| 发法 | 结果 |
|---|---|
| 裸 `GET …/receiveTaskExpansion` | **HTTP 404**（nginx 的 404 页 —— 网关路由不到） |
| `GET …/receiveTaskExpansion?acceptDate=`（**空值**） | **HTTP 200**，`{"code":500,"msg":"云朵已过领取有效期～"}` |

⇒ `acceptDate` **是路由条件**：这个参数在不在，决定这一枪有没有到应用层。
值可以是空的，**键必须在**。

## 为什么会错（这条比结论重要）

抓包回答的是「**线上字节长什么样**」，它**不回答**「这一枪能不能成功」。
当被观测的客户端自己就在传一个会失败的请求时，抓包会把**失败**如实记下来 ——
而读的人很容易把它当成"正确的形状"，因为它的措辞是"真实客户端发出去的"。

**判据**：一条抓包结论，要问它记录的是
①「客户端**发出**了什么」 还是 ②「**成功**的那一枪长什么样」。
这两者在正常路径上重合，所以平时分不出来 —— **只有在出错路径上才分叉**，
而抓包往往只在出错路径上才有样本（成功的那次没人去抓）。

## 这一条的教训

我上一轮把它当"权威"抄进了代码和注释（还写了"⚠ 不许写 `?acceptDate=`"），
幸好真机跑了一遍才发现是 404。**如果只跑单测（我写了 8 条全绿）永远发现不了** ——
因为夹具是照我自己的理解造的。

⇒ 所以目标里"每一族都要真机验一次"这条不是形式。

```
GET  /market/rabactive/ai/image/merge     404
POST /market/rabactive/ai/image/getStatus 405
GET  /market/rabactive/ai/image/getStatus 404
```

· 元数据标 `evidence: 'dead'`、`implemented: false`，note 里写明**两条读数与排除过的假设**

否则我改的只是"让读数看起来更顺眼"，而不是"让它能跑"。

## F-024 · 上传三枪**真机跑通** —— 路上吃了 4 个坑，全是单测发现不了的

```
✓ ① create    → fileId（33 字符）+ 预签名地址（**585 字符**）
✓ ② PUT       → 256 字节（HTTP 200）
✓ ③ complete  → 已确认
✓ 收尾        → HTTP 200 / success:true / code:"0000"
```

### 坑 ① 缺**头画像** ⇒ HTTP 404

这一族（`/hcy/file/*`）要一组自己的头：

```
x-yun-api-version: v1        x-yun-app-channel: 10000023
x-yun-op-type: <op>          x-huawei-channelSrc: 10000023
x-yun-client-info: <设备串>   x-yun-sub-op-type: <op*100>
```

少了就 **404** —— 而 404 **看着像"路径不存在"**（F-015 那个坑的第三次）。
出处：mcloud 的 `cloud_file_op_headers`。

### 坑 ② content-type 要 `application/json`，**不是** `oct-stream`

写 `oct-stream`/`octet-stream` 回 `04000018 请求体媒体格式不支持`。
⚠ mcloud 里那两个常量**是给别处用的**，我照抄错了地方。

### 坑 ③ `uploadUrl` 在 **`data.partInfos[0].uploadUrl`** 里

顶层**没有** `uploadUrl` 这个键。照顶层读的后果不是报错，而是
"看着像成功了却没有地址可用"。实拍：

```json
{"success":true,"code":"0000","data":{"fileId":…,"rapidUpload":false,"uploadId":…,
  "partInfos":[{"partNumber":1,"partSize":null,"uploadUrl":"https://hcyykj-eos-….cmecloud.cn/…"}]}}
```

✅ 交叉验证：真机量到的预签名地址**585 字符** —— 与抓包记的
"`uploadUrl` 583/585，**585 是照片那一发**"**逐字吻合**。

### 坑 ④ 收尾那一枪**不走 H5 签名**

`batchTrash` 在**云盘主机** `personal-kd-njs.yun.139.com` 上，要的是**云盘族的头** +
传输层注入的 `Authorization`。照 H5 签名（`m.mcloud.139.com` 那一族）发会回
**404 / `04000005 认证失败`**。

### ⚠ ⑤ 我自己的脚手架吃了一个 403，而它暴露了**真问题**

第一次 PUT 回 **403**。原因：`deterministicFile` 会产生 **NUL 字节**，
而我的验证脚本用 `execFileSync` 的 **argv** 传体 —— argv 里不能有 NUL ⇒ 被截断
⇒ `content-length` 与预签名覆盖的那个长度不符 ⇒ 403。

⚠ 但这条**不只是脚手架的事**：这一族把体当**字符串**交给宿主，
而"字符串里的 NUL 能不能原样过到线上"**没验过**。
⇒ `deterministicFile` 改成**只产出可打印字节**（0x21–0x7E），并加测试钉住"不许有 NUL"。
内容对"触发备份/过名字门"没有意义，所以这个改动不损失任何东西。

## 方法论：一次**只改一样**

坑 ① 与 ② 我一度**认错了因果**：第一次 404 时我同时改了两样（加头画像 + 改 content-type），
于是把 404 归因成 content-type，写下"要 `oct-stream`、写 json 会 404"——
**反了**。后来分开试才发现：404 是**缺头**，`oct-stream` 是**媒体格式不支持**。

⇒ 两个变量一起动，就会得到一个"能自圆其说但错"的结论。

### 三步与两个"坑"（都照实拍钉）

| 步骤 | 请求 | 坑 |
|---|---|---|
| ① | `POST user-njs.yun.139.com/user/querySpecTokenV2`，body `{"toSourceId":"017027"}` | 用的是**直播侧**的 `toSourceId`；混成签到的 `001005` 的表现是"一条房间都筛不出来"，而那看起来像**今天没有直播**（假结论） |

门本身的判据是 `status == 1` **且** 昵称**精确相等**。实拍那张表里就有

e2e 的夹具里刻意摆了这间房。

### ⚠ 一个刻意的取舍：**一次调用发两发**（而不是一发）

面板的纪律是「一次 handler 调用只发一个上游请求」，但这里**做不到**：
①换到的 SSO token **只活几分钟**（mcloud 实测注释：「换到 4 分钟后重放已被拒」），
而 cron 间隔是 10 分钟 ⇒ 把 ①② 拆成两次调用**必然**过期。所以：

```text
handshake 步：① querySpecTokenV2 → ② cmpassLoginByCmToken   （两发，同一次调用）
rooms   步：③ tabContentList(127) + ③ tabContentList(129)    （两发，同一次调用）
```

代价与理由都写进了 `liveGateTask.ts` 的文件头。最关键的一条是**它全是只读**：
万一真被 2000ms 预算判超时，上游一个字节都没改，重跑没有代价 ——
这也是它敢两发一次调用的原因（`live-draw` 那条写链就不敢）。

### 凭据处理：JWT 必须落盘，但**跑完就抹**

直播侧 JWT（≈30 天）要从 handshake 步活到 rooms 步 ⇒ 跨调用 ⇒ 必须落盘。
所以规矩定死三条：`done` 时 `delete`；接口**一律不回显**（e2e 断言
`'MOCK-LIVE-JWT' not in 响应`）；**每轮重新换一次**（照 mcloud 的 `gate_jwt`，不缓存跨轮）
—— 少写一个"票还有多久过期"的判据，就少一处会与上游真实有效期脱节的地方。

③ 失败时**丢掉 JWT 退回第一步**：门是只读的，重走没有代价；而留着一枚坏票会让
"票坏了"表现成"门一直是关的" —— 一个**假结论**，而假结论比失败难查得多
（mcloud 在参考实现上吃过这个亏，注释原话：「让"凭据坏了"表现成"门开着、
却一条口令也听不到"」）。

### 顺带**改正**一处我自己写错的判据文档

`koulingPool.ts` 里 `ProbeRoom.status` 的注释原先写「`0` 未开播 / `1` 直播中 /
**`2` 已结束（回放）**」—— **回放是 6，不是 2**（mcloud 的 `LIVE_ROOM_STATUS_ENDED = 6`，

"日程里没有回放"这种**看着正常**的空。已改正并写明校正日期。

## F-029 · WebSocket：挡住弹幕的不是协议，是**宿主没有这个能力**（2026-10-14）

F-027/F-028 里我一直把"WS / 弹幕"写成**结构性不可及**，理由是「面板的插件宿主没有
WebSocket」。这句话本身是对的 —— 但它是**面板侧的缺口**，而不是"这条链做不了"。
用户点了这一条，于是这一轮先补宿主能力：**没有口子，插件那边连试都试不了**。

### 面板侧补了什么（第二十一轮，`rust-plugin-panel` 996d204）

```text
ws_open(url, opts) -> {id}     握手失败就在这一步报错（不留半死的句柄）
ws_send(id, text)  -> {ok}     入队即返回（不等对端确认）
ws_recv(id, ms)    -> {type}   **带超时**：text / binary / timeout / close / error
ws_close(id)       -> {ok}     幂等
```

形态是**异步在 tokio 侧、同步在插件侧**：连接任务跑在面板的 runtime 上，
插件侧仍然是阻塞调用 + 超时。这一条对本插件特别关键 —— 本插件的整套写法是
「一次 handler 调用推进一步」（面板预算 2000ms），而 `ws_recv` 的超时正好对上：
**超时返回 = 这一步没收到东西**，状态落库、下一次调用接着收，
**插件侧不需要事件循环**，句柄跨调用有效。

三条最容易写错的语义（已写进面板的 `docs/host-api.md` 与插件的 `host-api.d.ts`）：

| 语义 | 判据 | 为什么不能反过来 |
|---|---|---|
| `{type:'timeout'}` **不是错误** | 等满了就是没东西 | 抛异常会把"正常等不到"表现成任务失败，把日志刷满 |
| 句柄不存在（关过了 / **面板重启过**）**抛异常** | 那是生命周期问题 | 静默当成 `close` 会让人以为"对端关了"，而处置完全不同 |
| 一次最多等 **1800ms** | 面板预算 2000ms | 别按"长连接就能一直读"写 |

边界（照抄面板那侧的实现）：同时最多 **8 条**连接、单帧上限 **256 KiB**
（超了报 `error` 并关掉，**不静默截断**）、**不自动重连**（退避与重放是插件的业务判断）、
TLS 与 `http_fetch` 同一个信任库（⇒「目标机不需要装 CA」仍然成立）。

⚠ **只有嵌入式 JS 宿主有**：PocketPy 与两个适配器都是"函数存在、调用时明确抛"。
所以本插件的 Node 测试（`node --test`）**不受影响**，前提是把 WS 调用收敛到一个
**可注入的端口**上（与 `transport` 同一个套路）—— 下一轮接弹幕时必须照这个写。

## F-030 · 实机（2026-10-14 15:0x，直播**正在进行中**）：门三步的判据全对上了；而**面板根本连不上那两个主机**（rustls vs CBC）

用户说「已经实机过了，现在也可以实机，直播正在进行中」。于是这一轮做真机验证，
结果一半是好消息、一半是**面板侧的硬边界**——两半都得如实记。

### 做法（纪律先写清）

```text
① 起一个面板实例（本仓的插件 + 面板的 WS 能力），**第一件事是把 mcloud 的 23 条任务全暂停**
   —— 否则 cron 会在真账号上写（`app-task` 每 15 分钟一跑，而 15:00 那一跑已经在导入凭据前发生过）
② 导入真凭据（从 mcloud 的 accounts.json 读，**不打印**）
③ 只跑**只读**的：live-gate（门）
④ 另开一个 Node 探针（Node 用 OpenSSL ⇒ 能谈 CBC 套件）把门的① ② ③ 逐字复核一遍
```

### 好消息：门的三个判据在**今天的真上游**上全部对上

| 步 | 实机结果 |

| ① SSO | ✅ `user-njs.yun.139.com/user/querySpecTokenV2`（TLS 1.3）→ 42 字符 token |

```text
页签 127  #147868 status=1 主播="中国移动云盘" 预告=2026-10-14 14:30  ← **那个主播，正在播**（门开着）
```

⇒ `status=6` 是**回放**（页签 129 里 7 间全是 6）✓ 与 F-028 更正的 `2 → 6` 一致。

### 坏消息（**面板侧的硬边界**）：那两个主机**只给 CBC 套件**，而面板用的是 rustls

面板里跑 `live-gate` 的真实结果：

```text
① 换 SSO ✅ 通过
② 换直播侧 JWT ❌ io: received fatal alert: HandshakeFailure
```

原因不是我们的代码，是 **TLS 能力不匹配**（用 openssl 逐条量出来的）：

```text
$ openssl s_client -connect v.cmcc-cs.cn:443 -tls1_2
  New, TLSv1.0, Cipher is ECDHE-RSA-AES128-SHA          ← 只有 CBC + SHA1 这一档
$ openssl s_client -connect videoim.cmcc-cs.cn:20102 -tls1_2   （**WS 那个主机也是**）
  New, TLSv1.0, Cipher is ECDHE-RSA-AES128-SHA
$ … -cipher "ECDHE-RSA-AES128-GCM-SHA256"               ← 只给现代套件
  alert number 40 (handshake failure)
```

面板的 HTTP 用 `ureq + rustls`、WS 用 `tokio-tungstenite + rustls`，而 **rustls 不实现
任何 CBC 套件**（设计选择，不是配置问题）⇒ **两个主机一个都连不上**。
也就是说：**直播这一族（门 + 弹幕）在面板里今天根本走不通**，卡在传输层，
与协议实现无关。mcloud 那边能跑，是因为它用的是 **native-tls（OpenSSL）**。

⚠ 这条同时解释了为什么"实机过"与"面板里实机过"是两件事 —— 前者是 mcloud（OpenSSL），
后者是面板（rustls），**同一份协议、两种 TLS 能力**。

### 下一步（明确的、不是"以后再说"）

给面板补一条**能谈 CBC 的路**，而且要**不破坏现有性质**（默认仍是 rustls、
musl 静态二进制不需要 OpenSSL）：

```text
选项 A（推荐）  cargo feature `legacy-tls`（默认关）：
                ureq 开 `native-tls`、tokio-tungstenite 开 `native-tls`，
                再给 http_fetch / ws_open 各加一个 `tls: "rustls"|"native"` 选项（默认 rustls）。
                · macOS 上 native-tls 走 **Security.framework**（不拉 OpenSSL）——
                  本机 cargo 缓存里 native-tls-0.2.18 / tokio-native-tls-0.3.1 /
                  security-framework-3.7.0 **都在**，能离线编
                · Linux/musl 要 OpenSSL ⇒ 所以必须**默认关**，只在需要直播那一族的构建里开
选项 B（mcloud 的选择）  「按主机分客户端」：把这两个主机名写进一张表，命中就走 native-tls。
                与 A 是同一件事，只是判据从"插件显式要"换成"宿主按主机名认"
```

在补上之前，**弹幕那一支在面板里连"连不上时如实报错"都算不上** —— 现在会报
`HandshakeFailure`，而那个措辞会让人以为是我们写错了协议（真因是 TLS 套件不重叠）。
所以补 TLS 的同时，错误信息也要能区分这两件事。

## F-031 · 实机（同一天 15:2x）：**面板真的连上了直播侧** —— 门的三步 + WS 的 `o` 帧，都是真上游给的

承 F-030：那一刻我认定「面板连不上那两个主机（rustls vs CBC）」。**结论没错，但它不是终点** ——
用户说"现在也可以实机"，所以我把那条路补出来了，并在**正在进行的直播**上验到真数据。

### 补的是什么（面板侧，`legacy-tls` 这个 cargo feature）

```text
默认构建（一个字节都没变）：ureq + rustls（http_fetch）、tokio-tungstenite + rustls（ws_*）
--features legacy-tls      ：多一条**能谈 CBC** 的路，插件用 tls:"native" 显式要
   · HTTP → reqwest(blocking) + native-tls
   · WS   → tokio-tungstenite 的 Connector::NativeTls
   · macOS 走 Security.framework（不拉 OpenSSL）；Linux 走 OpenSSL ⇒ 所以**默认必须关**
```

⚠ 两个实现细节值得记（都是"踩了才知道"）：
1. **不能直接开 `ureq/native-tls`**：它要 `der 0.8.2`，而本机离线缓存里只有 `0.7.10`
   ⇒ 半版本不兼容、离线编不出来。所以 HTTP 那条路换成 `reqwest + native-tls`
   （mcloud 生产用的同一套，缓存里全在）。
2. `tls:"native"` 在**没编这个 feature 的宿主里是明确报错**，不是静默退化：

```text
{"error":"tls:\"native\" 需要宿主用 `--features legacy-tls` 构建（本构建里只有 rustls；…）"}
```

   —— 实测确认（我先启动的是默认构建的二进制，拿到了这句话；换成 feature 构建后同一个调用就通了）。

### 实机结果 ②（本轮真正的目的）：**面板连上了直播弹幕的 WS，收到 SockJS 的 `o` 帧**

```text
URL  wss://videoim.cmcc-cs.cn:20102/ws/699/3jrpsvrn/websocket
句柄 1（typeof = number）                      ← 握手成功（CBC 套件，靠 native-tls）
```

这一条同时钉住了四件事（都是 F-029/F-030 里只能"推测"的）：

```text
① WS 端点的形状对：/ws/<serverId 0-999>/<sessionId>/websocket，Origin + iPad UA 都被接受
② 「面板有能力接长连接」这件事**从"能写出来"变成"实测到了"**（先前只有 mock 的假服务端）
③ ws_recv 的 timeout 语义在真环境里成立：`o` 之后没东西就是 timeout，**不是错误**
④ 弹幕那一支的**传输层已经通了** —— 剩下的只有 PROVISION/msync 那层（protobuf），
   而它已经有实拍文档（F-029 更正里那份 133 帧的样本）可以照着写
```

⚠ 仍然如实标档：**`o` 之后没有业务帧**（因为我没发 PROVISION）。所以
「弹幕文本能不能拿到」这件事，本仓**还没有**自己的实机证据 —— 它有别的证据面
（2026-09-23 的实拍 + Go 对拍），但**面板这条路**只走通到"连接已建立"。

### 实机结果 ③：**插件自己的 gate 任务**在真直播上跑通了（不是只有宿主 API）

把插件侧那条路也接上（`BuiltRequest.tls`，cmlive 那两枪带 `tls:'native'`），
重新打包后在同一个面板里触发 `live-gate` 两次：

```json
gate: {"at":"2026-10-14T07:25:47.010Z", "active":true, "liveCount":2,
       "rooms":[{"roomId":147868,"title":"重阳云盘存暖意！好礼赢不停！","status":1,
                 "expectStartTime":"2026-10-14 14:30:00","anchorNickname":"中国移动云盘"},
                {"roomId":147698,"title":"权益流量特惠购","status":1,
                 "expectStartTime":"2026-10-14 15:00:00","anchorNickname":"福建移动"}, …]}
pool: {"scheduleAtMs":1791962747010, "sessions":[{"startedAtMs":1791962747010}]}
```

⭐ `active:true` 就是门的结论（那个主播**在播**），而 `liveCount:2` 说明**同一刻有两间房在播**
—— 「按昵称精确匹配」这条判据不是洁癖，是必须的（F-028 的判据在真数据上站住了）。

⚠ `tls` 的**作用域**是一条判据，不是随手加的：`hostFetchOptions` 里加了
「**只对 `https:` 生效**」的守卫。理由是宿主对 `tls:"native"` 会**先校验再发请求**
⇒ 给 `http://` 的 mock 请求填它会直接报错 —— 而本仓 e2e **全程只打 mock**（`http://127.0.0.1`）。
没有这条守卫，e2e 就得改用 `--features legacy-tls` 的构建才能跑，那就把
"默认构建能不能跑 e2e"这件事给出卖了。
