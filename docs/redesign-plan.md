## 0. 为什么重构

现在的形态 —— 25 条任务、每条「一次调用只做一步」、五花八门的 cron、界面上
一堆黑话（"上游"/"矩阵"/"门"/"口令池"）、诊断全塞进"高级" —— 全都是从
**面板的 2 秒执行预算**倒推出来的。而那 2 秒不是用户的需求，是面板的限制。

真正的目标（用户原话）：

> 这个是有不同的用户部署在他的设备上用的……现在最烦的是对于其他用户来说难以使用明白。

所以：**一个不懂技术的人，装完之后能不能自己用明白**，是唯一的产品判据。
功能对齐 mcloud、压测面板边界，都退到次要。

## 1. 最终规格（已与用户逐条确认）

### 1.1 用户看到的东西

```
主面板侧边栏 → [mcloud]        ← 插件声明，面板渲染

  ┌ mcloud 插件页（菜单栏切换，一屏一块）──────────────┐
  │ [账号] [日常] [兑换] [直播] [数据] [推送] [设置]   │
  └────────────────────────────────────────────────────┘

  账号   扫码 / 短信 / 账密登录；多账号列表，选当前；设备号设置与轮换
  日常   一个大按钮：签到→…→领取。串行全账号，一天 1~2 次（可改，支持随机）
  兑换   设一个时间（如 10:00）：hh:59:40 进窗口 → 预热 → 整点前解滑块
         → 整点−10ms 发单。全账号**并行**（每个账号一条任务）
  直播   ① 手动：贴口令 → 串行全账号领
         ② 定时：开一个监听窗口（几小时）→ 听弹幕 → 自动领
         口令全场通用；200108(无效) 与 200118(本场已结束) 必须分开说
  数据   查询结果**直接看**（不是任务）：余额 / 奖品 / 快照 / 兑换清单 / App 矩阵
  推送   渠道配置 + 日常/兑换/直播各选一条规则
  设置   设备号、基址、直播主机、导入导出
```

### 1.2 任务模型

| | 旧 | 新 |
|---|---|---|
| 面板上可见 | 25 条 | **3 条**（日常 / 兑换 / 直播） |
| 单条任务 | 跨触发的状态机，「一次调用只做一步」 | **一个函数从头跑到尾**（跟 `mcloud-sign` 的 `executeAccount` 一样） |
| 为什么旧的要那样 | 2 秒预算 + `http_fetch` 同步阻塞 | 面板补「长任务独立线程」之后，这条约束消失 |
| 账号 | handler 内部循环 | **一个账号一条任务**（任务带参数）⇒ 兑换才能并行 |
| 查询 | cron 任务 → 写表 → 界面读 | **不是任务**，是读数（打开页面取，带"读到时间"） |

### 1.3 随机表达式（定稿）

| 写法 | 允许 | 规则 |
|---|---|---|
| `@every 5s -200ms` | ✅ | `@every` **只允许负偏移**，`-` 不能省，上限**周期的 20%** |
| `@every 5s ~1s` / `+2s` | ❌ | 报错：「间隔表达式只支持负偏移，例如 `@every 5s -200ms`」 |
| `*/5 * * * * * ~500ms` | ✅ | cron 宽松：`+` / `-` / `~` 都行 |
| `0 0 * * * ~30m` | ✅ | 范围限制保留（钳到相邻周期内） |

实现要点：

- `@every` 负偏移 ⇒ `actual ≤ base < next_base`，**单调性天然成立，不需要钳制、不会突发**
- cron 钳上界 `next_base - 1ms`（`*/5 * * * * * ~10s` 会被钳）
- **抖动不累积**：理论时间线自己走，抖动只加在实际那条上
  （面板现在 `scheduler.rs:455` 用 `t.next_fire` 推进 —— 加了抖动就变成随机游走）
- 手动触发 / 暂停恢复 / 熔断重试 / catch-up **都不抖**
- `lateMs` 要扣掉 `jitterMs`（否则 `diag` 的 p99 告警直接废掉）
- 测试种子走环境变量 `PANEL_JITTER_SEED`，**不进表达式**

### 1.4 登录

三种都做，**走插件路由、不进任务表**（mcloud 的 `login.rs` 自己也是这么说的：
「登录不是 Task —— Task 的契约是给我一个账号我跑完报结果，而登录没有账号可给」）。

- 扫码（`/api/login/qr` + 轮询）、短信（`/sms` + `/start`）、账密（`/password`）
- **设备号不是登录动作**，是请求参数（设置 + 轮换）
- 二维码插件自己画（`crypto/png.ts` 已有，加个 QR 编码即可）

### 1.5 推送

- 10 个渠道：PushPlus / Server酱 / 企业微信应用 / 企业微信机器人 / Telegram Bot /
  Bark / 双卡短信 / 钉钉机器人 / 邮件 / 自定义 POST
- **邮件走面板新补的 `smtp_send`**（其余 9 个都是 HTTP POST）
- 挂载点是**「一次运行结束」**（mcloud 的 `DigestMode::PerRun` 默认）
- 先做**简单版**：填渠道 → 日常/兑换/直播各选一条规则。更灵活的模型以后再说

### 1.6 日志

按**「一次运行」**组织，不是面板那 200 行环形缓冲。
插件自己的表 + 自己的界面：一次运行 = 一串步骤，每步带结论。

- [x] **①-1 插件声明式 worker 归属**　✅ `rust-plugin-panel` `7d6e41a`（第二十三轮）

  验收：`python3 scripts/worker_hint.py` —— 基线 9ms / 不声明+阻塞 310ms /

  顺带记下两个实测结论（`README.md` §16.26）：cron 比 `@every` 晚 3-9ms（根因未定位，

- [x] **①-2 任务带参数**　✅ `rust-plugin-panel` `b94a111`（第二十三轮）

  验收：`python3 scripts/params_check.py` —— 三条同处理函数的任务各拿各的、不串味、

- [x] **①-4 随机表达式（抖动）**　✅ `rust-plugin-panel` `d9894fb`（第二十三轮）
  `@every` 只允许负偏移、上限周期 20%（提前是安全的，单调性天然成立、不用钳制）；
  cron 三个方向都行、越界**钳制**到相邻槽位。理论线 / 实际线分开存 ⇒ 抖动不累积。

- [x] **①-5 `smtp_send`（发邮件）**　✅ `rust-plugin-panel` `b8643c1`（第二十三轮）
  裸 SMTP 客户端（`EHLO`/`STARTTLS`/`AUTH`/`MAIL`/`RCPT`/`DATA`），支持

- [x] **①-6 按任务/路由声明执行预算**　✅ `rust-plugin-panel` `0dbbe8a`（第二十三轮）
  **这一项是计划里漏掉的**：①-1 只解决了「长任务要独占线程」，但全局执行预算
  （`EXEC_BUDGET_MS=2000`）还在 —— 一个「一个函数从头跑到尾」的任务必然超过 2 秒，
  然后被判「疑似死循环」掐断。**没有它，阶段 ② 的日常/兑换/直播三条任务都跑不起来。**

      worker_hint('exclusive');   // 长预算必须配独占线程
      register_cron('日常', '*/30 7-22 * * *', runDaily, { budget_ms: 120000 });
      register_route('/plugins/x/run', 'POST', handler, { budget_ms: 120000 });

  范围 100ms ~ 10 分钟，越界报错；落 `jobs.budget_ms`（面板可见、重启还在）；
  长预算 + 没 exclusive ⇒ **加载期警告并点名插件**；没声明预算的任务**依然**被
  全局值拦下（保护还在，验收脚本里有对照组）。
  验收：`python3 scripts/budget_check.py`（14 项断言）全过。
  踩坑：**HTTP 那一层用的是全局预算** —— 路由声明 8 秒、Axum 侧 3 秒就 504，
  声明等于没声明。

### 阶段 ③ 兑换

- [x] ③-1 毫秒级那条链：hh:59:40 进窗口 → 预热两枪 + 500ms → 整点前取题解滑块
      → 整点−10ms 发单 → 514 重取题再下单　✅ 本条
      新增 `src/mcloud/exchangeTiming.ts`（**纯函数**）：两段等待 + 时刻读数。
      逐条照抄参考实现的边界 —— 尤其两条容易"顺手优化掉"的：
      ① **整点后 15 秒内仍算在窗口里**（上一场的尾巴）—— 砍掉它会让整点后
      0~15 秒内触发的每一次**白等 59 分钟**；② 算出来的目标时刻已经在过去时
      **不等**（硬等会等成负数）。
      **分工是这条链的核心**：粗粒度等待交给**调度器**（任务挂 `@every 10s`），
      细粒度（≤30 秒）才自旋 —— 自旋是为了把最后一枪压到 10ms，不是坐等 59 分钟。
      ⚠ **小时闸**（`STATE_ORDERED_HOUR`）：自旋期间排在后面的触发会积压，
      跑完之后它们立刻依次执行，而那时已过整点、链会判"现在就发"
      ⇒ **每一枪都真花豆**。下单不可逆、无幂等键，所以这道闸是必需品。
      它记的是"**发过**"不是"成功过"——代价不对称是刻意的。
      ⚠ 沙箱里**没有计时器**（面板明说"延时一律交给调度器"），所以毫秒级等待
      只能自旋。可接受的理由：兑换是**独占 worker** 的（只占自己那条线程）、
      看门狗按 `start + budget` 判定（预算内的自旋不会被杀）、一小时一次。
      验收：`test/exchangeTiming.test.ts` 24 项 · `split_check.py` 90 项（+11）。
- [x] ③-2 全账号（**串行 + 两阶段**，不是"一个账号一条任务"）　✅ 本条
      ⚠ **计划里这条原来是错的，核实之后改了**（见 F-046）。两条证据：
      ① **面板给不了插件内并行** —— worker 分配单位是**插件**
      （`engine.rs:423` 的 `route_map().get(plugin)`），而本插件又声明了
      `exclusive`（整个插件一条专属线程）⇒ 名下 N 条任务**必然串行**。
      "一个账号一条任务"只会让面板多出 N 行，拿不到任何并行。
      ② **参考实现自己也没做** —— `mcloud-engine/src/pipeline.rs` 对 `Parallel`
      **明确报错**，理由「上游常有限流，并发打过去容易触发风控」，
      而且专门写了「静默接受等于在界面上留一个后端做不到的开关」。
      参考实现用的是 `Sequential`。
      **所以按串行做，但做到位**：整点前那些活**不是时间敏感的** ——
      阶段 A 把每个账号都推到"只差下单"，阶段 B 整点−10ms 依次发单。
      整点那一刻每账号的代价从"整条链"（约 1.5s）降到"一枪"（约 0.15s）。
      ⚠ **越靠后的账号越晚这件事要说出来**：运行记录里每个账号都带 `离第一枪 +Nms`
      —— 不说的话用户只看到"失败"，不知道是排在后面导致的。
      实现细节：链的状态是**一整块** blob，两阶段之间要 `snapshotOrder` /
      `restoreOrder` 分别存（否则第二个账号的 `startOrder` 覆盖第一个的进度）。
      验收：`test/exchangeOrder.test.ts` 25 项（+3）。
- [x] ③-3 时间可配 + 状态显示　✅ 本条（`47c205f`）
      · **目标时刻可配**：`targetHour`（默认 10 点，参考实现是 `0 10 * * *`）；
        留空 = 每小时都试。用**本地时区**算 —— 用户说"10 点"指的是他的 10 点。
        窗口**跨整点**（(H-1):59:40 → H:00:15），所以判据不能只看小时数：
        09:59:40 的本地小时是 9，但它已经在 10 点那一场的窗口里了；0 点那场跨午夜。
      · **提前量可配**：`leadMs` 0~2000ms（默认 10）。它是**本地到云端的传输耗时
        补偿**，网慢的人该调大。越界被路由挡住 —— >2s 就不是补偿了，是"提前跑"。
      · **状态显示**：读数里有 `toTargetMs` / `targetHour` / `leadMs` / `inWindow` /
        `orderedThisHour`，界面第一行直接说人话
        （「离这一场还有 3 分 20 秒 · 每天 10 点 · 压整点前 10ms 发」）。
      ⚠ **顺带修了一个更要紧的东西**：任务挂 `@every 10s`，而清单请求原来排在
      时间判断**之前** ⇒ 一天 **8,640 次白打**。现在时间闸在**任何请求之前**，
      不在窗口里就零请求秒返回 —— 它是 `@every 10s` 能成立的前提，不是优化。
      ⚠ **「现在试一次」改成干跑**：清单/余额/预热/取题都做完，到"只差下单"就停，
      **一枪都不发**。按钮标签是"试一次"，用户想知道的是「现在能不能兑」——
      而那一枪发出去真扣豆且不可逆。真下单走「立即兑换」（会二次确认）或定时那一场。
      （顺手把 `runExchange` 从入口挪到 `tasks/exchangeRun.ts` —— 入口顶层会
      `register_cron`，路由 import 它会让任务被注册两遍。）
      ⚠ 一个被测试抓到的出口漏洞：干跑那条说明第一版加在函数**末尾**，而
      "没设兑换目标"是**提前返回**的 ⇒ 干跑路由的结果里看不出它一枪都没发。
      改成所有出口走一个 `finish()`。
      验收：`test/exchangeTiming.test.ts` 29 项（+5）· `split_check.py` 105 项（+15）。

## 3. 关键设计决定（含理由）

1. **拆插件，而不是给面板加「任务通道」**
   面板 `src/workers.rs` 写着硬约束：*「一个插件只能属于一条 worker，它的所有任务都
   跟着它。分配的单位是**插件**，不是任务。」* 所以要让日常和兑换分开跑，
   正解是按族拆插件 —— 而面板的「起名即分组」已经会把 `mcloud-*` 聚成一块。

2. **协议层一行不动**
   `crypto/*`（纯 JS 的 md5/sha/aes/des/rsa/png/gzip/hmac）、上游客户端层、
   各任务的协议逻辑、mock 与黄金向量、findings 里那些**真机才暴露的洞**
   —— 这些是真金白银。作废的只有**编排层和状态机**。

3. **登录不进任务表**（见 §1.4）

4. **查询不是任务，是读数**（见 §1.2）

5. **推送挂在「一次运行结束」上**
   mcloud 的模型是「一次运行推一条」（`DigestMode::PerRun` 默认）。
   面板现在**没有「一次运行」这个概念**，所以没有那个时刻可以发 —— 这正是
   「推送无法实现」的根因，不是缺个 HTTP 调用。
