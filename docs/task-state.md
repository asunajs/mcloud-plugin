# 任务状态：本地记录不是成功

> 2026-10-20 现场：106「手动上传一个文件」本机已经上传、也已经发了 `task/click`，
> 本地 `apptask.state` 记成 `done`，但上游矩阵一直是 `WAIT / currStep 1`。
> 结果是当天不再重试，界面上看起来像"根本没做"。

## 硬规则

1. **只有服务端明确表示完成才算成功。**
   App 任务以矩阵里的 `state === 'FINISH'` 为唯一判据。
   HTTP 200、本机上传成功、本机发过 `task/click`，都只是"动作做了"，不是成功。
2. **本地记录只记动作和证据，不记成功。**
   `mcloud.upload.state` / `mcloud.apptask.state.clicked` 是"我们做过什么"，
   不是"这件事完成了"。
3. **未确认的条目不能挡住重试。**
   收摊时仍在待办里的条目从 `clicked` 移到 `unconfirmed`；
   `appTaskFresh()` 看到未确认项就返回 `false`，下一趟重新起链。
   **不限制重试次数**：只要服务端没回 `FINISH`，下一趟继续试；
   重试次数只写日志，不参与"今天做完了"的判断。
4. **记录必须带有效期。**
   - 每日任务：`day` 不是今天就无效；不能拿昨天的 `done` 挡今天。
   - 每月任务：跨月无效；月门用当月读数，不沿用上月。
   - `unconfirmed` 也按 `retryDay` 划界，昨天未确认不影响今天。
5. **「刷新」必须真请求。**
   `GET /matrix` 默认只读本地；`?refresh=1` 才真正打移动云盘
   （两个市场各一发），并把结果写回矩阵缓存。界面上的刷新按钮走后者。
6. **动作和复查之间必须有时间间隔。**
   不能刚上传/打卡完，就拿**动作前**的矩阵快照判「没变」。
   App 任务收摊时先进入 `settle`，等 `settleMs`（默认 5 秒）后
   重新拉两个市场的矩阵，再决定 `FINISH` / `unconfirmed`。
   没到时间只报「等服务端确认」，不报成功，也不提前判失败。

## 现场例子（106）

| 证据 | 值 | 含义 |
| --- | --- | --- |
| `upload.state.step` | `done` | 文件确实传完了 |
| `apptask.state.clicked` | `[106]` | 发过打卡，但**不是**成功 |
| 矩阵 `state` | `WAIT` | 服务端不认，任务仍未完成 |
| 结论 | 未完成 | 下一趟可以重试；UI 显示「本机已请求（服务端未确认）」 |

## 代码位置

- `src/mcloud/tasks/appTask.ts`：`advance()` / `appTaskFresh()` 的确认与重试规则。
- `src/mcloud/routes.ts`：`/matrix` 的本地读与 `?refresh=1` 真刷新。
- `plugins/mcloud/app.js`：任务状态卡的本机证据、刷新按钮。
