# 领奖：待领取奖品 → 短信验证码

> 界面上的第六块「领奖」。用户点进来的三件事：**选账号 → 看未领取 → 点「领取」→ 填短信验证码**。
>
> 协议与判据来自 **2026-10-31** 的实拍（另一个仓库 `../mcloud-capture`）：
> `mcloud/upstream/h5-getprize-claim.md`（成文）与
> `mcloud/capture/app-getprize-samples.txt`（三笔 `code:0`、`flag` 逐笔 1 → 2）。
> 本文件只写**这个插件实现了什么、哪些还没被证实**，不重复抄那份抓包。

## 1. 它长什么样

```
领奖
  2 件待领取                                  ← 第一行回答"有几件"
  点「领取」会发一条短信验证码到 159****7542   ← 第二行说清副作用
  ┌ 待领取 ──────────────── [账号 ▾] [刷新] ┐
  │ 0.41元支付宝话费红包                     │
  │ 全网算力大作战 · 过期 10-31 23:59 · 159****7542   [领取] │
  └──────────────────────────────────────────┘
        ↓ 点「领取」（弹窗自动发码）
  ┌ 领取 · 0.41元支付宝话费红包 ──────────────┐
  │ 验证码已发到 159****7542，填进来就能领到。 │
  │ [ 短信验证码 ]            [确认领取]       │
  │ [重新发送（60 秒）]                        │
  └──────────────────────────────────────────┘
```

**界面上没有滑块图，也没有"输入偏移量 / 像素"这种格子** —— 那几像素人眼分不出来，
让用户填等于让他猜。滑块由后端本地解（见 §3）。

⚠ 「日常」最后那一步的「待领取奖品」读数**仍然是旧行为**：走云朵中心那个单市场口
（`signin/public/record?marketname=sign_in_3_ex`），所以它数出来的件数可能比这一页少。
这一页用官方「待领取」旧口（跨市场），**以这一页为准**；那一处没跟着改是为了不动日常链的
请求形状（改它要连带改日常的 mock 与 e2e）。

## 2. 接口（插件自己的三个路由）

| 路由 | 语义 |
|---|---|
| `GET /plugins/mcloud/api/prizes?account=&refresh=1` | 读待领取（**只读**，按账号，60 秒缓存；跨市场） |
| `POST /plugins/mcloud/api/prizes/claim` `{account,oid}` | 详情 → 取滑块并本地解 → **发验证码短信** |
| `POST /plugins/mcloud/api/prizes/confirm` `{account,oid,code}` | 提交验证码 → **真正领取** |

响应约定：

* 列表读失败是 **HTTP 200 + `failed`**（照常渲染，页面写"读不到 —— 原因"）；
  `failed` 可能与 `items` 同时出现（第 1 页有货、第 2 页挂了）——**不吞已有结果**。
* `claim` / `confirm` 的业务失败是 **HTTP 200 + `{ok:false, note}`**（人话）。
* 只有"账号不存在 / 没先发码 / 缺参数"才是 **400 + `{error}`**。
* 响应里**没有** `jwttoken` / cookie / `deviceId`；手机号只有脱敏形态。

## 3. 为什么必须自己解滑块

`getSlidePuzzle` 的两张图：

| 字段 | 格式 | 用途 |
|---|---|---|
| `puzzle` | **PNG** 96×400 RGBA 竖切片 | 只有碎片本体不透明；碎片在切片里的 y = 它在底图里的 y |
| `picture` | **JPEG** 680×400 | 底图；`puzzleLeft` 恒 `null`（服务端不给答案） |

`puzzleOffset` = **碎片左边缘在 680 宽底图里的 x**，可滑范围 `0…584`。
实拍里人工值 277 与算法值 286 差 9px 仍被接受，第三笔用算法值 526 **直接通过**
⇒ 服务端容差至少 ±9px，算法值可以直接用。

本仓的做法：

1. `src/crypto/jpeg.ts` 解 `picture`（基线 JPEG；progressive 明确报错）；
2. `src/crypto/png.ts` 解 `puzzle`；
3. `src/mcloud/slide.ts::calcSlideOffset` 用**轮廓梯度**在 `0…584` 上扫一遍，
   取峰值；`usable()` 要求 `offsetX > 0` 且置信度 ≥ 1.5；
4. **算不出来就不发** `sendPrizeSms` —— 发出去只会白耗一次题面（与兑换那条同一口径）。

> ⚠ "算不出来"不是"少一次机会"，而是"多一次确定失败"。界面上没有手动填像素的兜底；
> 用户能重试（后端会换一道新题），但不会看到一个要他量像素的格子。

## 4. 领取链（照实拍，逐条）

```text
getUserPrizeLogPageV2 (flag=1 待领取，**旧口**、不传市场)
  └─► receivePrizeDetailsV2 (marketId / prizeId / drawRecode=oId)
       └─► getSlidePuzzle (POST {})
            └─► sendPrizeSms {oid, puzzleOffset, app:0}   ← 发短信
                 └─► acceptPrizeV2 {oid, app:0, sendDefaultSms:true,
                                    source:"1000", smsCode, deviceId}
```

四个"照实拍、不顺手改"的地方：

1. **列表只用旧口**。官方「奖品（待领取）」页用的就是它，不传市场 ⇒ 110 条 / 13 个活动；
   云朵中心那个新口（`signin/public/record`）**只覆盖 `sign_in_3_ex` 一个市场**，
   算力大作战那笔它看不见（2026-10-24 实测）。⇒ 只用新口会漏。
   ⚠ 旧口的单号是 `oId`（大写 I），新口是 `oid` —— 两个都认。
2. **不预先调 `queryAcceptExt`**。实拍里页面没发这一条（静态调用点被短路），
   三笔都是"详情 → 滑块 → 发码"。我们照跑通的那条路走；`smsFlag` 语义没被实拍证实，
   不拿它当闸。
3. **验证码是 `MD5(用户输入的码)`（32 位小写 hex）**，只有 `prizetype` 为
   `1028` / `1029` 时发明文。别"统一明文"。
4. **`isdeviceid: true` 只有 `acceptPrizeV2` 那一枪带**（逐接口，不是一刀切）。

## 5. 还没被证实的（写清楚，不假装做了）

| # | 未知 | 现在的做法 | 第一次真跑看什么 |
|---|---|---|---|
| 1 | `deviceId`：实拍三笔都是 **84 字符 base64**（App 客户端档案），生成规则未核 | 用会话里那个 H5 设备指纹（`B…`，与 `receiveV3` / `exchangeV3` 同源） | 若被拒，读数会指出是确认那一步；届时换来源（若 App 档案能从别处拿到） |
| 2 | `sendSpaceGiftPrize`（空间礼包那一发）实拍未触发 | 不做 —— 领取成功不依赖它 | 空间礼包类奖品是否会在榜单里留下"已领取" |
| 3 | `flag=10` 的含义（0.5 元话费红包那一格） | **不猜**：不进列表，也不当已领取 | 那一格以后会不会自己变 1 |
| 4 | `queryAcceptExt` 的 `T.value` 置真时机 | 不调用 | 不需要 |
| 5 | 各错误码的实拍样本（静态码表） | 只做查表翻译（`prizeCodeText`） | 撞到时把码与处理记进本节 |
| 6 | 详情里 `verifycode` / `sms` 的语义（是不是"这一件要短信"） | **不拿它做闸**：一律走"发码 → 填码"（三笔实拍都是这条） | 遇到"不需要短信"的奖品时，会不会收不到码 / 该不该直接确认 |

## 6. 安全与副作用

* **会发真的短信**（到账号绑定的手机）。所以只有用户点「领取」才发；同一件
  60 秒内本地不重发（上游有"获取验证码频繁" 1001）。
* **领取不可逆**（没有幂等键）。所以：`claim` 与 `confirm` 拆成两步，
  中间那一步的等待由用户决定 —— 和登录那条链同一个理由。
* 验证码与 `deviceId` **不进日志**；手机号只以脱敏形态出现：
  列表的 `servNumber` 与**账号标签**都在领奖边界过一遍 `maskPhoneLike`
  （账号默认标签就是完整手机号，不能指望"上游会脱敏"）。
* **写操作不自动重试**（`sendPrizeSms` / `acceptPrizeV2` 都没有幂等键）：
  写之前只做"票过期就换一轮票"；换不成让用户自己再点，**不替他重跑**。
  没拿到回应时标 `unknown`：发码那步落一单（短信可能真发了，收到还能填），
  确认那步**清掉这一单**并让用户先刷新列表看结果 —— 不许拿同一个码再撞一次。
* 读失败/写失败都**不吞**：`failed` / `{ok:false,note}` 一路带到界面。

## 7. 怎么在没有真账号的情况下验证

### 一条命令（真面板 + mock，不碰真账号）

```bash
./scripts/e2e-prize.sh <面板可执行文件> 18870
```

它起 mock + 面板、建一个假账号、导入假会话，然后**走完整条链**：列表（只出 flag=1 的两件）
→ 点「领取」（真跑 JPEG 解码 + 滑块匹配，答案 282）→ 提交 `MD5("123456")`
→ mock 侧 `flag` 翻 2 / `prizeAccepted` 有单号 → 再读列表只剩 1 件（命中缓存）。
同时断言：列表/日志里没有 jwttoken / cookie / deviceId / 验证码摘要，手机号是脱敏的。
本机实测那一枪（3 个请求 + 解码 + 解滑块）约 **2.0 秒**（面板沙箱里）。

### 手工

```bash
# mock 上游带一题"能解"的滑块（JPEG 底图 + PNG 切片，答案 282）
node mock/upstream.mjs 18900
# 插件基址指到它（走 /plugins/mcloud/api/config）并加一个账号，然后：
#   GET  /plugins/mcloud/api/prizes
#   POST /plugins/mcloud/api/prizes/claim   {"account":"…","oid":"1280973030"}
#   POST /plugins/mcloud/api/prizes/confirm {"account":"…","oid":"1280973030","code":"123456"}
```

mock 会验：`puzzleOffset` 与 282 差超过 15 ⇒ 回 `514`（滑块失败）；`smsCode` 必须是
`MD5("123456")`（1028 那一档例外）；没发码直接确认 ⇒ `-7`；领成功后 `flag` 翻 2。
夹具的来历与重生成命令见 `mock/fixtures/README.md`。

单元/路由测试：`node --test test/prizeClaim.test.ts`（列表过滤/去重、发码、MD5、
冷却、滑块算不出就**不发**、确认态过期、错误码、路由缓存与凭据不回显）。
JPEG 解码器：`node --test test/jpeg.test.ts`。
