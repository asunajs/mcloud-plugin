## 2. "❌ 没搬"为什么不动

参考实现的原话（`app_task.rs:917`）：**判不出形状 ⇒ 一个请求都不发**。
真机账单也在（2026-10-14 那次）：548/549/550/607 四条各点一枪，**全回 HTTP 200、状态一条没变** ——
点了不改状态，只会把"没做"伪装成"做了"。所以这一档**保持一枪不发**，日志里如实说"还没搬"。

要真做它们，得先有实拍形状（像 1020 那样三发、1029 那样五发），不是加一行 `click`。

## 10. #434 分享 `0/7` 一直不动（2026-11-01 15:0x，用户截图）

真因：分享那一格**读的是全局上传槽** `mcloud.upload.state`，而槽里躺的是**上一趟/已收尾**的文件
（522 传完就进回收站了）⇒ 拿一个**已删的 fileId** 去建外链，上游回
`1010010006 …记录已被删除 / 消息参数错误`。

改法：**分享只用"这一趟自己新传的那一枚"** ——
`advance` 遇到 434 一律 `beginUpload`（不看上传槽），`share` 阶段只认 `st.fileId`，
传完直接进分享（以前会被 `afterClick` 顺手删掉）。

真机（三个号各跑一趟）：

```
打卡 #434 → 手里没有文件 → 自己传一个 → create/put/complete → 外链已建(1) → 删外链 → 收尾
矩阵：434  第 4 步 · 分享文件领好礼 1/7   ✓ 计数动了
```

⚠ **上游一天只记一次分享**（参考实现 `SHARE_DONE_STATE_KEY` 的注释：同一天第二次分享不加数）
⇒ `7/7` 要 **7 趟（7 天）**，不是一趟能刷完的。
